1. wshobson/agents

#1 · ~36.3k ⭐ wshobson/agents

단일 Markdown 소스에서 5개 AI 코딩 하니스(Claude Code · Codex · Cursor · OpenCode · Gemini)용 에이전트/스킬/커맨드를 생성하는 멀티-하니스 플러그인 마켓플레이스.

MIT 84 plugins192 agents 156 skills16 orchestrators

개요

프로덕션용 agentic 워크플로 빌딩블록 모음. 하나의 .md 정의를 make generate로 각 하니스의 네이티브 포맷으로 변환 — "최소공통분모 번역"이 아니라 하니스별 idiomatic 산출물을 만든다. 도메인 전문가 에이전트를 플러그인 단위로 격리하고, 설치한 플러그인의 컴포넌트만 컨텍스트에 로드한다.

아키텍처

  • 플러그인 중심: plugins/<name>/ 안에 agents/ commands/ skills/
  • 컴포넌트는 디렉터리 구조에서 자동탐색
  • 오케스트레이터 전용 플러그인: agent-orchestration, full-stack-orchestration, conductor, agent-teams …

대표 컴포넌트

  • backend-architect — API·마이크로서비스 경계 설계
  • security-auditor — OWASP 취약점 진단
  • context-manager — 멀티에이전트 세션 상태 관리
  • full-stack-feature (command) — end-to-end 기능 오케스트레이터
  • plugin-eval — 3계층 품질평가(정적/LLM judge/몬테카를로)

오케스트레이션 (가장 정교한 사례)

  • 오케스트레이터는 별도 에이전트가 아니라 slash command(.md) 절차서 — 메인이 Task로 서브에이전트 spawn
  • 파일 기반 상태: 각 단계 산출물을 .full-stack-feature/stepN.md로 기록 → 다음 단계는 컨텍스트 메모리가 아닌 그 파일을 Read (컨텍스트 윈도우 비의존)
  • state.json(current_step / completed_steps / files_created)으로 세션 재개(resume)
  • 병렬 = "한 응답에서 다중 Task 호출": test-automator + security-auditor + performance-engineer 동시 spawn
  • Phase 체크포인트에서 AskUserQuestion으로 게이트 후 진행

모델 전략 & 정의 포맷

README는 4-tier 권고(Tier1 Opus=중대 결정 / Sonnet=문서·테스트 / Haiku=운영)지만, 실제 파일 frontmatter 기본값은 model: inherit(호출자 모델 상속)였다 — 문서 권고와 파일 기본값이 어긋남.

--- (backend-architect.md, 실제 확인)
name: backend-development-backend-architect   # 플러그인 prefix 네임스페이스
description: Expert backend architect... Use PROACTIVELY when creating new backend services.
model: inherit
---

약점

  • make generate 멀티하니스 파이프라인이 무겁다
  • 에이전트 본문이 장문 → 컨텍스트 비용↑, 모델 의도 불명확

우리가 가져올 것 ★

  • 파일 기반 오케스트레이션: 오케스트레이터를 slash command로 만들고 단계 산출물을 .task/stepN.md로 기록 → resume까지. cheap-context 직결
  • "한 응답 다중 Task = 병렬" 명문 규칙 + Phase 게이트
  • frontmatter에 "Use PROACTIVELY when…" 트리거 + model: inherit, 단 본문은 더 짧게

2. VoltAgent/awesome-claude-code-subagents

#2 · ~21.1k ⭐ VoltAgent/awesome-claude-code-subagents

10개 카테고리로 조직된 154+ 프로덕션급 서브에이전트 정의 카탈로그. 별도 런타임 없이 Claude Code 네이티브 .claude/agents/ 위에서 동작.

MIT154+ agents 10 categoriesmeta-orchestration 카테고리

10개 카테고리

  • Core Development (11)
  • Language Specialists (31)
  • Infrastructure (16)
  • Quality & Security (17)
  • Data & AI (13)
  • Developer Experience (15)
  • Specialized Domains (14)
  • Business & Product (16)
  • Meta & Orchestration
  • Research & Analysis (11)

대표 컴포넌트 (조정 계층)

  • agent-organizer sonnet — 팀 조립·작업 분해·능력 매칭 (계획)
  • multi-agent-coordinator opus — 동시 실행·동기화·실패 처리 (실행)
  • task-distributor — 작업 할당·로드 밸런싱
  • codebase-orchestrator — 리팩터링 거버넌스
  • error-coordinator — 에러 복구 조정

오케스트레이션 — 명시적 3계층 분리 (핵심 차별점)

계획(agent-organizer) → 분배(task-distributor) → 실행(multi-agent-coordinator) 의 역할이 분리돼 있다. 한 코디네이터가 분해+실행을 다 하지 않는다. coordinator는 scatter-gather / fork-join 으로 병렬 분배하고, 의존성에 topological sort, 데드락에 circular detection, 자원에 priority scheduling을 적용(프롬프트 수준 서술).

정의 포맷 (가장 정제된 템플릿)

---
name: agent-organizer
description: "Use when assembling and optimizing multi-agent teams..."  # 트리거형
tools: Read, Write, Edit, Glob, Grep   # 화이트리스트
model: sonnet
---
# 본문 골격: 역할 → "When invoked" → 도메인 체크리스트
#           → Communication Protocol(JSON 컨텍스트 요청) → 3단계 워크플로 → Integration

약점

  • 본질적으로 정적 프롬프트 카탈로그 — 런타임 검증·실측 성능 없음
  • 오케스트레이션이 "한다고 적어둔" 서술이지 실제 보장 메커니즘 아님; 154개 전부 깔면 라우팅 충돌 우려

우리가 가져올 것 ★

  • 계획/분배/실행 3계층 분리 — 분해 에이전트와 실행 코디네이터를 분리
  • 트리거형 description + 3필드 frontmatter(name/description/tools/model)로 자동 라우팅 정확도↑
  • Communication Protocol: 워커가 시작 시 필요한 컨텍스트만 구조화 요청 → 거대 JSON 통째 Read 방지

MIT24 agents 3 orchestrators13 framework specialists

오케스트레이션

name: tech-lead-orchestrator
description: ...MUST BE USED for any multi-step development task...
tools: Read, Grep, Glob, LS, Bash
model: opus    # 무거운 역할=강모델 (단 README엔 문서화 안 됨)

약점

  • 오케스트레이터 "직접 구현 금지 + 병렬 N개 제한" → 평가서버 4코어에 맞춰 상한 2~4 명시
  • 판단 역할(critic/오케스트레이터)엔 강모델, 단순 워커엔 경량 모델

7. 우리 셋업 도입 권고
