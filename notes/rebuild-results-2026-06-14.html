핵심 발견

Rebuild는 realize barrier를 충실히 돌파한다 — CP-SAT 전역 z3 최소화로 20인스턴스 중 16개에서 z1=0 도달. 그러나 천장은 크레인-안전 패킹 밀도다. z1 소거를 위한 블록 퇴거가 z3를 선형적으로 올리고, 경쟁자 수준의 z3는 경쟁자 수준의 패킹 밀도 없이 도달 불가능.

W2 — 패킹 순서 포트폴리오

W3 — LBBD 베이별 용량 캡-컷 (CP-SAT)

OGC_W3=1 z3는 CP-SAT로 해결 z1 barrier 확인
  • _cpsat_assignment로 전역 z3 최소 배정을 구하고 디코드 오라클을 돌린다. tardy 베이의 면적 캡을 반복적으로 축소(LBBD cap-cut).
  • 데이터가 가르친 것 ①: prob_1에서 z3=2 달성 — 경쟁자(z3=8)보다 낮다! CP-SAT는 z3를 경쟁자 수준으로 풀 수 있다. 그러나 z1=6이 남았다. 즉 배정은 최적인데 디코더가 크레인 직렬화를 해소 못 하는 것.
  • 데이터가 가르친 것 ②: 면적 캡 절감(area relaxation)은 필요조건이지 충분조건이 아니다 — CP-SAT가 캡을 만족하는 크레인-충돌 배정을 반복 발견. 진동(oscillation)하고 수렴하지 않음. 해법은 W4의 조합 컷.
  • 버그 발견: Phase-2 SA가 예산을 독점해 prob_3에서 LBBD가 한 번도 실행되지 않음 → 순서 재배치: LBBD 우선, SA는 마지막 polish.

W4 — 조합 ban-컷 + timing-in-loop

OGC_W4=1 4/20 @100s · 6/20 @100s (w4b) z3 과-스필
  • 캡-컷이 stall하면 tardy 베이에서 z3-최저 블록을 퇴거(evict)하는 조합 컷으로 전환. timing-in-loop: 고정 시각 z1 ≤ THRESH일 때 per-bay timing oracle을 호출해 진짜 z1을 확인한 뒤 컷 생성.
  • 데이터가 가르친 것 ①: ban-컷이 캡-컷이 막힌 곳을 뚫는다 — prob_3 z1=0이 3라운드에서 달성. 하지만 6번의 ban이 필요해 z3가 105→599로 급등 (baseline 407보다 나쁨).
  • 데이터가 가르친 것 ②: timing oracle이 z1을 거의 움직이지 않는다 (prob_5: fixed_z1=26 → true=24). 지연은 타이밍 문제가 아닌 기하적 과밀(geometric over-subscription). 스태거링으로 해소되는 z1이 거의 없어서 "필요 없는 퇴거"가 줄지 않는다.
  • 데이터가 가르친 것 ③: prob_14에서 27라운드 ban이 obj를 600,128(z1=27)로 올림 — 수렴 실패 시 legacy fallback 예산이 고갈.

5핵심 발견 — 천장 = 패킹 밀도, 점진 레버 소진

Pivotal conclusion (2026-06-14 REFLECTIONS): Legacy와 rebuild 모두 동일한 천장에 막혀 있다 — 크레인-안전 패킹 밀도(crane-safe packing density). Rebuild는 realize barrier를 충실히 돌파(16/20에서 z1=0)하지만, 기하적 과밀을 해소하는 유일한 방법인 퇴거가 z3를 올린다. 탐색을 더 해도 이 구조를 벗어날 수 없다.

EXACT decoder 실험 — 레버 종료 (closed)

프로브에서 exact _decode_bay가 raster보다 z1을 25–35% 더 해소했다 (prob_3: 23→15, prob_5: 92→65, prob_12: 484→370). 기계적 원인: exact _decode_bay는 entry time을 순서화(sequence)하는 반면 raster의 _fixed_time_decode는 entry=R 고정 → 강제 시간 공존 → 크레인 충돌. 이것이 아키텍처가 명시한 "진짜 오라클"이었고 raster 대체가 z3 천장의 원인이었다.

관찰 1 — timing oracle은 z1을 거의 안 움직인다

per-bay timing oracle을 loop에 적용해도 prob_5에서 fixed_z1=26 → true=24. 지연은 타이밍 문제가 아니라 기하적 과밀 — 어떤 타이밍에도 블록들이 크레인-안전하게 공존 불가. 레버 소진.

관찰 2 — legacy가 rebuild보다 z3가 낮다

prob_3: legacy z3=407 vs W4 z3=599. 동일한 raster 디코더를 쓰는 legacy의 Front-B relocate+swap이 ban-컷보다 z3 탐색에 효과적. 고정 시각 과다계산이 불필요한 퇴거를 유발. 레버 소진.

구조적 결론: 배정 최적화(W3 CP-SAT)로 z3는 경쟁자 수준(prob_1 z3=2)에 도달 가능함이 증명됐다. 병목은 그 배정을 실현할 때 크레인 직렬화를 발생시키지 않는 디코더 — 즉 더 조밀한 크레인-안전 패킹이 유일한 진짜 레버다. 이 범주 내의 모든 점진적 레버(타이밍·exact decode·컷 전략·용량 보정·SA)는 전부 소진됐다.

구조적 변화: 블록을 criticality 순(tight-slack 우선)으로 처리하면서 (bay, position, entry-time)을 동시에 결정 — marginal cost w1·tardiness + w2·Δz2 + w3·pref-dev 최소화, crane-safe LCA placement. 크레인-가능한 위치에만 배치되므로 realize barrier가 구조적으로 존재하지 않는다. z1/z2/z3를 블록당 균형 결정(기존 CP-SAT는 z1-blind).

CP-SAT bay-target 합성: 순수 greedy는 z2+z3 조합 최적을 못 찾음(prob_1 z3=452 → 대참사). 해법: uconstruct가 먼저 CP-SAT 전역 z2+z3 최적 배정을 구하고, 블록별로 그 target bay를 우선 시도 — z1=0으로 실현되면 커밋(CP-SAT 최적 상속), 아니면 최소 스필. 결과: CP-SAT의 z2+z3 전역 최적과 greedy의 z1=0-by-construction이 처음으로 결합됨.

  • Unified가 이들 인스턴스에서 내는 obj는 경쟁자 대비 40~100%+ 초과 — target bay 합성이 over-subscribed preferred bay에서 스필을 충분히 줄이지 못함.
  • Legacy도 동일 구조로 패배 — Front-B relocate+swap이 z3를 더 이상 내릴 수 없는 local minimum에 수렴.
  • 공통 근본 원인: preferred bay의 crane-safe 공존 블록 수가 경쟁자 대비 적음 → 불가피한 과-스필 → z3가 2~4× 높음.

13/20 달성 프론티어: (a) 더 조밀한 crane-aware 패킹(블록 공존 수를 경쟁자 수준으로 올리는 packing/sequencing 알고리즘), 또는 (b) unified의 per-instance 버그 수정(prob_11 과-구독, prob_3 고착) + CP-SAT target 예산 증가로 가까운 flip 획득. 어느 쪽도 현재의 incremental 레버 범위를 벗어난 연구급 빌드가 필요하다.

OGC == 출판된 Shipyard Block Spatial Scheduling (SSP)

이 문제는 공개 학술 도메인의 Shipyard Block Spatial Scheduling (SSP)과 동일하다. 적용 가능한 방법이 이미 존재한다.

발견출처적용
LCA (Largest-Contact-Area) 배치 — 후보 위치 중 이미 배치된 블록+벽과의 접촉 면적이 최대인 위치 선택. BL "가장 낮은 y,x" 타이브레이크 대체. 간격 낭비 최소화 → 밀도 향상. Shang & Gu 2017 (BCA/LCA); Koh 2008 핵심 레버
Diagonal-fill (BL+TR 앵커) — BL 앵커만이 아니라 TR·TL·BR도 고려해 후보 집합 생성 ("양방향 슬라이드"). 빈 공간의 대각선 구석 채우기. Kwon & Lee 2015 (Comp&IE) 핵심 레버
Extreme-Point 후보 집합 — 베이 모서리 ∪ 배치된 블록의 특징점(TL,TR,BL,BR) 전체를 후보 집합으로. BL-abut 단일 후보보다 훨씬 조밀. Gardeyn 2026 (MergeDJD/Sparrow) 후보 생성
Jostle / overlap-min ILS — 교대 좌우 재삽입 패스(shaking)로 간격 재충전. 느린 개선 refiner. Martinez-Sykora 2018; Imamichi 2009 보조 (느림)
경쟁자 유력 방법 — He, Hong, Kim 2024 (J. Scheduling) "Quick and situ-aware spatiotemporal scheduling": phase 1 = bay + start-date 배정, phase 2 = 정확한 (x,y) + 방향. 5–47초 근-최적 프로파일과 일치. 우리 재설계와 동일 분해 구조. He 2024 (Hyundai 검증) 경쟁자 분석
크레인 j≥k 제약은 SSP 문헌에 없다 — 기존 SSP 논문 전체가 이 제약을 다루지 않는다. footprint-raster(fftconvolve) BLF는 층 인식이 없어 크레인-불안전한 배치를 생성. 레이어-인식 raster가 필수. 내부 분석 (prob_3/5/12/20) 주의 — naive 적용 금지

블록은 대부분 2-LAYER (prob_3 86/100, prob_5 123/150, prob_12 171/200, prob_20 254/300) → crane j≥k 하강 규칙이 실질적으로 작동 — 기존 _ft_search_pos / fastfloor._verify 로직 보존 필수.

9근본 원인 + 다음 레버

근본 원인 — 퇴거-z3 오버슈트: 우리의 _cpsat_assignment area-time 캡은 필요조건이지 충분조건이 아니다. CP-SAT는 캡을 만족하는 크레인-충돌 배정을 반복 발견 → 디코더 z1 >0 → ban-cut이 더 많은 퇴거를 추가 → z3가 최적량보다 훨씬 초과. 예: prob_5 우리 z3=602 vs 경쟁자 z3=94.

bay0 과-구독: 배포 창 기준 면적 164% — 대부분 zero-slack 블록(due = R+P, 스태거링 불가) → 패킹도 time-repositioning도 모두 해소 불가. 일부 블록은 반드시 퇴거해야(z3 비용). 경쟁자는 64% 초과분을 저렴하게(z3=94) 퇴거, 우리는 훨씬 많이(z3=602) 퇴거 — 캡의 느슨함이 ban-cut 오버슈트를 유발.

최우선 다음 레버: packer-calibrated capacity

  • packer를 써서 베이별 진짜 crane-safe block capacity를 실측.
  • cap_alpha[j]를 그 실측값으로 설정 → CP-SAT가 진짜 용량 제약 하에서 min-z3 배정을 풀어 최소한의 z3 퇴거를 한 번에 결정(ban-cut 반복 오버슈트 없음).
  • packer(밀도 진실)와 assignment(z3 최적화)를 연결하는 누락된 링크.

보조: best-of packer-on/off — pkfull200의 경로 민감도 회귀(prob_5/6/9)를 제거하기 위해 packer ON / OFF 두 경로를 각각 풀고 최종 best 선택.

Time-repositioning(지연 허용 + crane 접근 확보)은 zero-slack 지배 구조에서 제한적. 배정 수준 해결(packer-calibrated cap)이 1순위.
