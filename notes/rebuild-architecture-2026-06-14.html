2진단 — 왜 현재 구조로는 안 되나

배정 단계 목적함수 (현재)

_cpsat_assignment  (myalgorithm.py : 1675)
  min  c2·z2  +  c3·1000·Σpref           ← z3-dominant
  ⚠ z1 은 목적함수에 없음 (z1-blind)

z1 = 0 달성은 배정 이후 디코드 + 타이밍이 사후(post-hoc) realize. 막히면 ban-rebuild가 블록을 선호 베이에서 추방 → z3를 되돌려 토해냄.

z3 갭의 본질

낮은-z3 배정이 z1 = 0으로 realize 안 됨 = realize barrier

  • 마스터가 z3-최적 배정을 산출
  • 디코더(crane j≥k) 통과 못 함 → z1 폭발
  • ban-rebuild: 블록을 선호베이서 추방 → z3 급등
  • z3 + z1 둘 다 나쁜 해로 수렴

이전 z3-race가 실패한 이유

  • z1을 마스터 목적에 미포함
  • cut이 약함 (블록-베이 ban만)
  • 완화(area-cap proxy)만 조임 — 충분조건 아님
  • realize barrier를 제거하지 않고 우회만 시도

3realize barrier = Benders Relaxation Gap

핵심 통찰 문헌 근거: #115 #121 #145 #146

우리의 AddCumulative area-time proxy는 필요조건이지 충분조건이 아니다.
낮은-z3 마스터 최적해가 완화 영역엔 있지만 realizable 영역 밖 → 디코드 시 z1 폭발.

잘못된 접근 (현재)

완화를 더 강하게 조이기 → proxy 정밀도 향상 시도

→ 조여도 충분조건은 안 됨. NP-hard gap.

올바른 접근 (LBBD)

진짜 디코더를 feasibility 오라클로 사용

→ realize 안 되는 배정을 no-good cut으로 제거

근거: Nascimento 2024 EJOR (#145) · Zipfel 2024 (#146) · Hooker et al. (#115, #121) — LBBD / branch-and-check 패러다임

4아키텍처

LBBD 루프 플로우

PRIMARY — LBBD / branch-and-check

  • 마스터: 배정 + 타이밍, 진짜 w1·z1 + w2·z2 + w3·z3 목적
  • 서브: crane-aware 디코더 = realizability 오라클
  • realize 실패 시 → no-good 부분집합 cut 생성 → 마스터 재최적
  • lazy cut(branch-and-check)으로 100s/300s 예산 준수

FALLBACK — z3-aware Constructive + ALNS

  • z3-aware constructive seed (crane-anticipatory insertion)
  • tardiness/z3-타깃 ALNS (디코더-in-loop repair)
  • PRIMARY 서브문제와 동일 코드패스 공유
  • PRIMARY timeout 또는 초기해 부재 시 fallback
격리 원칙

재설계는 새 모듈 + 플래그 OGC_REBUILD로 격리. 기존 파이프라인(gate200_v2, banrace, fastfloor) 완전 보존. 롤백 가능.
