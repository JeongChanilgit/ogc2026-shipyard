CP-SAT 성능 튜닝·스케일링·안티패턴

도메인 타이트닝, big-M 회피, 정수 스케일링, 병렬 워커, 힌트 웜스타트, 로그 해독, 큰 인스턴스 분해 전략까지 — 그리고 CP-SAT가 MIP(Gurobi)를 이기는 경우와 지는 경우. 실측 안티패턴과 OGC2026 특화 지침 포함.

⬡ OGC2026 관련성

환경: 평가 서버 4코어·16GB·인스턴스별 수분~30분 — GPU 없음, 인터넷 차단. 이 챕터의 모든 기법이 직접 적용된다.

  • 도메인 타이트: horizon = max(EXIT) 이 아니라 블록별 R+P 기반 tight upper bound. 좌표 도메인은 베이 크기(정수 단위)로 정확히 — 부동소수점 없이 정수 그리드.
  • 정수 좌표: 이미 정수 격자 — float 스케일링 오버플로 위험 없음. 단, Z2(작업부하 불균형) 계산 시 면적 누적값 오버플로 주의 (int64 한계 ≈ 9.2×10¹⁸).
  • 힌트 이월: legacy solver의 최종 배정을 CP-SAT timing oracle에 힌트로 전달. fix_variables_to_their_hinted_value=True로 배치 고정 후 타이밍만 최적화 = 탐색 공간 1-D 압축.
  • per-bay 분해: 베이별 독립 CP-SAT 서브로 분해 → 각 서브에 4코어 할당 가능. num_workers=4가 시간규율 유지의 핵심 — set2 타임아웃 → −1 회피.
  • legacy plateau 인식: legacy 솔버는 ~140–300s에서 obj 정체. CP-SAT oracle이 그 이후 유일한 개선 레버 — max_time_in_seconds를 남은 예산에 맞춰 동적 설정.
  • never −1 규칙: status in (OPTIMAL, FEASIBLE) 확인 후 반환. 시간 초과 시 반드시 베이스라인 greedy 해 fallback — CP-SAT UNKNOWN 반환이면 이전 최선해 사용.

1. 도메인 타이트닝 (Domain Tightening)

CP-SAT의 propagation 엔진은 도메인 크기에 직접 비례하는 탐색 공간을 처리한다. 변수 하나의 도메인이 [0, 10000] 대신 [0, 200]이면 전파 효율이 수십 배 향상된다. 이것이 가장 저렴하고 가장 효과적인 성능 레버다.

변수 도메인 좁히기 — 전/후 비교

# ❌ 안티패턴: 느슨한 도메인
horizon = 10_000_000                          # 알 수 없으니 크게 잡음
entry = model.new_int_var(0, horizon, "entry_1")
exit_ = model.new_int_var(0, horizon, "exit_1")

# ✅ 베스트프랙티스: 블록별 tight bound
earliest = block["ready_time"]                # R_i
latest_entry = max_makespan - block["proc_time"]  # 수식으로 상한 증명
entry = model.new_int_var(earliest, latest_entry, f"entry_{i}")
exit_ = model.new_int_var(earliest + block["proc_time"],
                           max_makespan,      f"exit_{i}")
model.add(exit_ >= entry + block["proc_time"])
model.add(exit_ <= block["due_time"] + MAX_ALLOWED_TARDINESS)

presolve로 자동 타이트닝 확인

solver.parameters.fill_tightened_domains_in_response = True
solver.parameters.log_search_progress = True

status = solver.solve(model)

# presolve가 좁힌 도메인 확인
for i, var_proto in enumerate(solver.response_proto.tightened_variables):
    if var_proto.domain:
        print(f"var {i}: tightened to {var_proto.domain}")
Tip — horizon 계산법

실현가능 최대 스케줄 길이(horizon)는 모든 블록의 max(ready_time) + max(proc_time)으로 상한을 잡되, 실제 실현가능 범위(마감일 기준)로 추가 타이트닝하라. OGC처럼 베이별 독립 스케줄이면 베이별 horizon을 별도 계산한다.

안티패턴 — "안전하게 크게"

new_int_var(-10**9, 10**9, "x") 같은 기본값 설정은 CP-SAT에서 치명적이다. 도메인 크기가 클수록 presolve가 생성하는 auxiliary constraint가 지수적으로 늘어난다. 실제 필요 범위를 수식으로 증명하고 정확히 설정하라.

2. big-M 회피 — OnlyEnforceIf / 반복(Reification)

전통 MIP의 big-M 기법은 CP-SAT에서 propagation을 약화시킨다. M이 크면 bound propagation이 제공하는 정보가 사실상 0이 되기 때문이다. CP-SAT는 only_enforce_if()로 완전한 대안을 제공한다.

big-M vs. OnlyEnforceIf

# ❌ big-M: propagation 무력화
M = 1_000_000
model.add(start[i] >= release[i] - M * (1 - assigned[i][j]))
model.add(start[i] <= due[i]     + M * (1 - assigned[i][j]))

# ✅ OnlyEnforceIf: 정확한 half-reification
model.add(start[i] >= release[i]).only_enforce_if(assigned[i][j])
model.add(start[i] <= due[i]).only_enforce_if(assigned[i][j])

조건부 누적 (Conditional Cumulative)

# 베이 j에 블록 i가 배정될 때만 demand 기여
demand = model.new_int_var(0, block_area[i], f"demand_{i}_{j}")
model.add(demand == block_area[i]).only_enforce_if(assigned[i][j])
model.add(demand == 0).only_enforce_if(assigned[i][j].negated())
# cumulative에 전달
model.add_cumulative(intervals_j, [demand_i_j, ...], bay_capacity[j])

Full Reification (양방향)

# b가 True ↔ constraint 충족 — add_bool_or/and로 구현
b = model.new_bool_var("feasible")
model.add(x <= 100).only_enforce_if(b)          # b=True → x≤100
model.add(x >= 101).only_enforce_if(b.negated()) # b=False → x≥101
안티패턴 — 과도한 Reification

only_enforce_if를 모든 제약에 과도하게 쓰면 LP 완화 품질이 떨어진다. M이 작고 tight하면 big-M도 허용되지만, 일반적으로 M ≥ 1000이면 OnlyEnforceIf로 전환하라. feasible.club 3년 경험: "reification의 loose big-M 상수가 propagation 강도를 약화한다."

3. Boolean 인코딩 선호

CP-SAT의 핵심은 CDCL(Conflict-Driven Clause Learning) SAT 솔버다. Boolean 변수로 표현된 문제는 이 엔진이 가장 잘 처리한다. 정수 변수도 내부적으로 Boolean 리터럴로 인코딩되지만, 처음부터 Boolean으로 모델링하면 presolve가 더 강력하게 단순화한다. 

# ❌ 정수로 표현된 할당
bay = model.new_int_var(0, num_bays - 1, f"bay_{i}")  # 모든 베이 값 탐색

# ✅ Boolean 배열로 할당 (CP-SAT 강점 구간)
assigned = [model.new_bool_var(f"assign_{i}_{j}") for j in range(num_bays)]
model.add_exactly_one(assigned)                      # 정확히 1개 베이

# add_exactly_one은 add_bool_xor / sum==1보다 훨씬 강력한 propagation
# add_at_most_one 도 유사하게 효율적
# Boolean 논리 직접 활용
b1 = model.new_bool_var("cond_a")
b2 = model.new_bool_var("cond_b")

model.add_implication(b1, b2)        # b1 → b2
model.add_bool_or([b1, b2])          # b1 OR b2
model.add_bool_and([b1, b2])         # b1 AND b2
Tip — add_exactly_one vs. sum == 1

model.add(sum(assigned) == 1) 대신 model.add_exactly_one(assigned)를 쓰라. 후자는 CP-SAT 내부에서 특수 처리되어 propagation이 훨씬 강하다. 마찬가지로 add_at_most_one도 선형 sum 제약보다 우월하다.

4. 부동소수 → 정수 스케일링

CP-SAT는 순수 정수 엔진이다. float 계수는 목적함수에만 제한적으로 지원되며 제약 내에서는 불가능하다. 스케일링 시 두 가지 위험이 있다: (1) 정밀도 손실과 (2) int64 오버플로.

스케일링 헬퍼 패턴

import math

def scale_to_int(value: float, scale: int = 1000) -> int:
    """float → 정수 스케일링, 오버플로 사전 체크 포함"""
    result = round(value * scale)
    INT64_MAX = (1 << 63) - 1
    if abs(result) > INT64_MAX:
        raise OverflowError(f"Scaled value {result} exceeds int64 range")
    return result

SCALE = 1000                    # 소수점 3자리 정밀도

# 가중치·비용을 스케일링
w1_s = scale_to_int(prob_info["w1"], SCALE)   # e.g. 667.5 → 667500
w2_s = scale_to_int(prob_info["w2"], SCALE)

# 목적함수도 같은 스케일
model.minimize(w1_s * tardiness_total + w2_s * imbalance + ...)

오버플로 위험 계산

# 최악 계수 추정: 스케일 × 값 범위 × 변수 수
# int64 한계 ≈ 9.2 × 10^18
max_coeff   = 1_000          # SCALE
max_value   = 10_000_000     # 예: 최대 타디니스
num_blocks  = 200
product = max_coeff * max_value * num_blocks   # 2 × 10^12 — safe

# SCALE=10^6이면 10^6 × 10^7 × 200 = 2×10^15 — still safe
# SCALE=10^9이면 10^18 × 200 — OVERFLOW RISK!
안티패턴 — 과도한 스케일 팩터

SCALE = 10**9처럼 정밀도를 위해 너무 큰 스케일을 쓰면 계수 곱이 int64(9.2×10¹⁸)를 초과할 수 있다. CP-SAT는 오버플로를 조용히 wrap-around하므로 디버그가 극히 어렵다. CP-SAT 계수 내부 한계는 ±2^63−1 — 스케일 × 도메인 크기 × 변수 수의 곱이 이 범위 안에 있어야 한다.

안티패턴 — 런타임이 스케일에 선형 비례

CP-SAT Primer 실험: 어떤 문제는 resolution(스케일 팩터) 증가에 런타임이 선형 비례하고, 다른 문제는 로그 비례였다. 스케일을 올리기 전 반드시 작은 인스턴스로 프로파일링하라. 필요 정밀도만큼만 스케일링한다 — "혹시 모르니 크게"는 금물.

5. 병렬 워커 (num_workers)

CP-SAT는 포트폴리오 솔버다 — 여러 워커가 서로 다른 전략(LP 집중, pure SAT, LNS heuristic 등)으로 동시에 탐색하고, 발견된 해와 bound를 공유한다. MIP처럼 탐색 공간을 분할하는 방식이 아니므로, 워커 수와 성능 관계가 비선형이다.

워커 설정 패턴

import os

# 방법 1: 명시적 설정
solver.parameters.num_workers = 8

# 방법 2: 물리 코어 수에 맞춤 (hyperthreading 제외)
physical_cores = os.cpu_count() // 2   # HT 고려
solver.parameters.num_workers = max(1, physical_cores)

# 방법 3: 평가서버 4코어 기준 OGC 설정
solver.parameters.num_workers = 4      # 4코어 = 안전한 상한
solver.parameters.max_time_in_seconds = time_budget

안티패턴 — "코어 많을수록 빠르다"

위 실측처럼 워커가 많을수록 메모리 대역폭 경합·스레드 동기화 오버헤드가 dominate할 수 있다. 특히 메모리 집약적 Boolean 문제에서 단일 워커가 최속인 경우가 빈번하다. 하이퍼스레딩 코어는 실제 물리 코어의 60~80% 성능 — num_workers를 물리 코어 수로 제한하라.

Tip — 워커 수 vs. 솔버 전략

num_workers = 1: LP 없이 순수 SAT+propagation → 작은 이산 문제에서 빠름.
num_workers = 2~4: LP 워커 + SAT 워커 조합 → 대부분 스케줄링 문제에 균형.
num_workers ≥ 8: LNS heuristic 워커 추가 → 큰 문제 feasibility 탐색에 유리.

6. 힌트 웜스타트 (Solution Hints)

CP-SAT의 힌트는 초기 해의 시작점을 제공해 presolve 이후 탐색이 좋은 incumbent를 빠르게 찾게 한다. 전통 MIP warm start와 달리 CP-SAT 힌트는 presolve 후 살아남은 변수들에 대해서만 작동한다. 

# 이전 단계(legacy/greedy) 해를 힌트로 전달
for i, block in enumerate(blocks):
    model.add_hint(assigned[i][bay_assignment[i]], 1)
    model.add_hint(entry_time[i], entry_from_greedy[i])
    model.add_hint(exit_time[i],  exit_from_greedy[i])
    model.add_hint(x_pos[i],      x_from_greedy[i])
    model.add_hint(y_pos[i],      y_from_greedy[i])

# 힌트를 고정값으로 사용 (배치 고정 후 타이밍만 최적화)
solver.parameters.fix_variables_to_their_hinted_value = True

# 타이밍 변수만 남기고 최적화 — 탐색 공간 1-D 압축
status = solver.solve(model)
# 힌트 실효성 확인 (로그에서 "HINT" 라인 찾기)
solver.parameters.log_search_progress = True
solver.log_callback = lambda s: print(s) if "HINT" in s or "#1" in s else None
안티패턴 — 부분 힌트

힌트가 일부 변수만 커버하거나 presolve 이후 불가능한 값이면 조용히 무시된다. 디버그가 어렵다 — log_search_progress=True로 초기 해 시간을 확인하고 힌트 없는 경우와 비교하라. 힌트된 해가 feasible하지 않으면 CP-SAT는 힌트를 버리고 처음부터 탐색한다.

7. 검색 로그 해독 (log_search_progress)

CP-SAT 로그는 성능 병목을 진단하는 핵심 도구다. log_search_progress=True로 활성화하면 표준 형식으로 출력된다.

로그 활성화

solver.parameters.log_search_progress = True
solver.parameters.log_to_stdout = False    # 기본값 True
solver.log_callback = lambda msg: print(msg, flush=True)

8. 큰 인스턴스 처리 — 분해 전략

8.1 시간 예산 할당

def solve_with_budget(model, total_budget: float, reserve: float = 30.0):
    """전체 예산의 일부를 CP-SAT에, 나머지를 heuristic에 배정"""
    cp_budget = max(10.0, total_budget - reserve)
    solver.parameters.max_time_in_seconds = cp_budget
    status = solver.solve(model)
    if status in (cp_model.OPTIMAL, cp_model.FEASIBLE):
        return extract_solution(solver, model)
    else:
        # fallback: greedy/legacy solution
        return baseline_solution

8.2 per-bay 분해 패턴 (OGC 직접 적용)

def solve_all_bays(prob_info, time_limit):
    """베이별 독립 CP-SAT 서브 → 결과 병합"""
    results = {}
    bay_time = time_limit / len(bays)    # 균등 분배

    for bay_id in bays:
        blocks_in_bay = [b for b in blocks if assigned_to_bay(b, bay_id)]
        if not blocks_in_bay:
            continue

        model = cp_model.CpModel()
        # 베이 내 타이밍 최적화만 (배치 고정)
        entry, exit_ = build_timing_model(model, blocks_in_bay, bay_id)

        solver = cp_model.CpSolver()
        solver.parameters.num_workers = 4           # 서버 4코어 풀 활용
        solver.parameters.max_time_in_seconds = bay_time

        status = solver.solve(model)
        if status in (cp_model.OPTIMAL, cp_model.FEASIBLE):
            results[bay_id] = extract_timing(solver, entry, exit_)
        else:
            results[bay_id] = greedy_timing(blocks_in_bay)  # never -1

    return merge_results(results)

8.3 증분 모델 재사용 (매 반복 재구축 금지)

# ❌ 매 반복 모델 재구축 — 큰 오버헤드
for iteration in range(max_iter):
    model = cp_model.CpModel()       # 매번 새로 빌드
    add_all_constraints(model)
    solver.solve(model)

# ✅ 모델 재사용 + 힌트 업데이트
model = cp_model.CpModel()
add_all_constraints(model)           # 한 번만 빌드

for iteration in range(max_iter):
    model.clear_hints()              # 힌트만 갱신
    for v, val in current_solution.items():
        model.add_hint(v, val)
    solver.solve(model)
안티패턴 — 루프 안에서 모델 재구축

매 LNS 반복마다 CpModel()을 새로 만들고 모든 제약을 다시 추가하면 모델 빌드 오버헤드가 실제 해 탐색 시간과 비슷하거나 초과할 수 있다. 모델 구조는 고정하고 힌트·assumption만 바꿔라. 또는 assumptions API를 사용하라.

안티패턴 — 불필요한 중간 변수

계산 결과를 모두 변수로 저장하는 습관은 메모리를 크게 낭비한다. CP-SAT에서 변수 1개는 내부 Boolean 리터럴 ≈ 수십 byte를 소비한다. 선형 식으로 인라인 표현 가능한 것은 별도 변수로 만들지 말라. 특히 집계(sum)는 변수 없이 바로 목적식에 넣을 수 있다.

11. CP-SAT vs. MIP (Gurobi) — 언제 무엇을?

OGC2026 조선소 블록 배정 문제는 CP-SAT의 강점 구간에 해당한다. 왜 그런지, 반대로 MIP가 우세한 경우는 어떨 때인지 정리한다.

특성 CP-SAT 유리 MIP/Gurobi 유리
변수 타입 순수 정수·Boolean 위주 연속 변수 다수 (LP 비중 높음)
제약 구조 Disjunctive (노겹침·순서), 이진논리 연속 LP 완화가 tight한 선형 구조
LP 완화 품질 약해도 propagation으로 보완 강한 LP bound → 빠른 분기한정
초기 feasible 해 빠름 (portfolio heuristic) MIP 경우에 따라 느릴 수 있음
스케줄링 (job shop 등) 강함 — No-Overlap, Interval 네이티브 disjunctive MIP formulation 필요
패킹·배치 Boolean 인코딩으로 처리 연속 좌표 처리 시 유리
모델 안정성 작은 제약 추가 시 성능 민감 변경에 더 robust
대회 성적 MiniZinc 2024 전 금메달 순수 LP/MILP 벤치마크 우세

OGC2026 적용 판단

# OGC 타이밍 서브문제 = CP-SAT 명확한 강점
# - 변수: entry/exit 정수 시간 (정수 도메인)
# - 제약: NoOverlap (disjunctive), crane j≥k (Boolean 논리)
# - 목적: tardiness 합 (정수 계수 선형 조합)
# → Gurobi disjunctive 논문 대비 CP-SAT이 최적해를 더 빠르게 증명
# (참고: arxiv 2512.11864 — 병렬기계 스케줄링 비교)

# OGC 배치 서브문제 = CP-SAT도 MIP도 어려운 영역
# - 2D 이형 폴리곤 패킹 → NFP 없는 CP-SAT이 직접 최적화 어려움
# - 실용 전략: greedy 배치(fast) → CP-SAT 타이밍 오라클(최적화)
# = 본 프로젝트의 핵심 decoupling 기법
⬡ 결정 근거 — "왜 Gurobi 아닌 CP-SAT?"

평가 서버에 Gurobi 13.0.2 풀 라이선스가 설치되어 있음에도 CP-SAT가 유효한 이유:

  • 타이밍 제약(crane j≥k, NoOverlap)이 disjunctive 구조 — CP-SAT의 절대 강점
  • Gurobi disjunctive formulation 실험 결과: prob_14에서 CP-SAT 161s vs Gurobi 267s (기각)
  • 연속 변수 비중 낮음 — Gurobi LP bound 이점이 희석됨
  • CP-SAT는 OR-Tools 임포트만으로 의존성 없이 작동 — firejail 인터넷 차단 환경에서 안전
