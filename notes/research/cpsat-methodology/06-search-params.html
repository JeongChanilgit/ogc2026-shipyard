CP-SAT Methodology · Chapter 06

탐색 전략 & 솔버 파라미터 튜닝

OR-Tools CP-SAT의 300개 이상 파라미터 중 실무에서 가장 중요한 것들 — 시간·종료 제어, 병렬 포트폴리오, 프리솔브, LP/컷, 탐색 분기 전략, 결정론적 재현, 로그 해독 — 을 실측 파라미터명과 Python 코드로 정리한다.

OGC 2026 관련성

평가 서버: 4 CPU 코어, 16 GB RAM, 인스턴스당 수 분~30 분.
핵심 적용: num_workers = 4(또는 8 + interleave_search), max_time_in_seconds를 남은 벽시계에 맞게 적응 설정, log_search_progress = True로 고원(plateau) 조기 감지, random_seed로 결정론적 재현.

운영 노트: 4-worker CP-SAT는 conda run으로 실행 시 크래시 발생 → 반드시 C:/Users/peter/anaconda3/envs/ogc2025/python.exe 직접 호출로 우회. 현재 src/ 하이브리드 솔버는 이 방식으로 안정 동작 확인.

1. 시간·종료 제어

max_time_in_seconds

벽시계 기준 최대 실행 시간. 기본값: 무한대(inf). 이 값을 설정하지 않으면 복잡한 모델은 무한 실행된다. 

solver = cp_model.CpSolver()
solver.parameters.max_time_in_seconds = 120.0  # 2분 제한

# 남은 시간 기반 적응 설정 (OGC 패턴)
import time
_start = time.time()
def remaining(reserve=5.0):
    return max(1.0, timelimit - (time.time() - _start) - reserve)

solver.parameters.max_time_in_seconds = remaining(reserve=10.0)
Best Practice
개발 중엔 60~300초로 시작, 제출 전 실제 인스턴스 크기에 맞게 확장. SolveWithSolutionCallback에서 콜백으로 남은 시간을 추적하면 더 정밀하다.

stop_after_first_solution

첫 번째 실현 가능한 해를 발견한 즉시 탐색 중단. 기본값: False. 목적함수가 있어도 최적화 없이 즉시 반환한다. 

solver.parameters.stop_after_first_solution = True
# feasibility check, warm-start seed 확보에 유용
함정
최적화 문제에서 무심코 ON하면 매우 나쁜 초기해로 제출된다. warm-start 힌트 검증(fix_variables_to_their_hinted_value)과 조합할 때만 의도적으로 사용.

relative_gap_limit / absolute_gap_limit

relative_gap_limit: |obj - bound| / max(1, |obj|) ≤ limit 이면 조기 종료. 기본값: 0.0 (비활성).
absolute_gap_limit: |obj - bound| ≤ limit 이면 종료. 기본값: 1e-4 (정수 문제에서는 사실상 최적 수렴과 동일). 

solver.parameters.relative_gap_limit = 0.02   # 최적의 2% 이내면 종료
solver.parameters.absolute_gap_limit  = 1000  # 1000 단위 이내면 종료
함정
relative_gap_limit = 0.05처럼 크게 잡으면 아직 개선 여지가 많을 때 조기 종료된다. 경쟁 상황(OGC처럼 상대 점수 방식)에서는 절대 갭 기준이 더 직관적. "갭 = 0%"는 증명된 최적을 의미하지만, 바운드 자체가 느슨할 수 있다.

2. 병렬 워커 & 포트폴리오

num_workers (구 num_search_workers)

병렬 실행 스레드 수. 기본값: 0 (자동 → 모든 논리 코어 사용). num_search_workers는 deprecated이지만 num_workers=0일 때는 여전히 읽힌다. 

solver.parameters.num_workers = 4   # 4코어 서버에서 권장
# 구형 코드 호환 (deprecated, 피할 것)
# solver.parameters.num_search_workers = 4

워커 수에 따른 서브솔버 포트폴리오 (실측, Laurent Perron 확인):

workers활성 서브솔버
1default_lp 단독 (결정론적)
2~4default_lp + no_lp + LNS workers (rnd_var, rnd_cst, graph_var, graph_cst, rins, rens)
5~7위 + first_solution subsolver 추가
8~9위 + max_lp + fixed + pseudo_costs + core + feasibility_pump
9+위 + quick_restart
11+위 + quick_restart_no_lp
13+위 + probing + lb_tree_search
32+전체 15개 full-problem solver + 증가된 first-solution workers
4코어 최적 설정 (OGC 서버 기준)
# 옵션 A: 4 workers — 보수적, 메모리 안전
solver.parameters.num_workers = 4

# 옵션 B: 8 workers + interleave — 더 많은 전략 다양성
# (컨텍스트 스위칭 오버헤드 있지만 LNS 다양성 ↑)
solver.parameters.num_workers = 8
solver.parameters.interleave_search = True
Laurent Perron: OR-Tools 튜닝은 8 및 16 workers를 주요 타깃으로 한다. 4코어 실제 실행에서는 8 workers + interleave가 pure 4 workers보다 LNS 다양성 확보 면에서 우위일 수 있다.
함정: workers 과다 설정 시 메모리 폭발
각 워커는 독립적인 모델 복사본과 LP relaxation을 유지한다. 대형 모델(수만 변수)에서 workers = 32로 설정하면 수십 GB RAM이 필요할 수 있다. OGC 서버 16 GB 제한 → max_memory_in_mb = 12000으로 안전망 설정 권장.

interleave_search

기본값: False. True로 설정하면 모든 주요 탐색 전략을 인터리빙하여 num_workers로 배분한다. 고정 스레드 할당 대신 Round-Robin 방식으로 서브솔버를 번갈아 실행 → 적은 코어 수에서도 다양한 전략 실험 가능. 

solver.parameters.interleave_search = True
solver.parameters.num_workers = 8  # 인터리빙 효과 극대화

subsolvers / extra_subsolvers / ignore_subsolvers

포트폴리오 서브솔버 커스터마이징. subsolvers는 전체 목록 교체, extra_subsolvers는 기본 목록 앞에 추가, ignore_subsolvers는 glob 패턴으로 제외.

알려진 서브솔버 이름 (로그에서 확인 가능):

  • Full-problem solvers: default_lp, max_lp, no_lp, fixed, pseudo_costs, core, lb_tree_search, quick_restart, quick_restart_no_lp, probing
  • LNS (incomplete) solvers: rnd_var_lns_default, rnd_cst_lns_default, graph_var_lns_default, graph_cst_lns_default, rins_lns_default, rens_lns_default, feasibility_pump
from ortools.sat import sat_parameters_pb2

# 특정 서브솔버 비활성화 (예: LP 없는 순수 CP 모드)
solver.parameters.ignore_subsolvers.append("max_lp")
solver.parameters.ignore_subsolvers.append("*lp*")  # glob 지원

# 커스텀 서브솔버 추가 (패킹 문제에서 유용)
custom = sat_parameters_pb2.SatParameters()
custom.name = "custom_no_lp_lns"
custom.linearization_level = 0
custom.use_lns_only = True
solver.parameters.subsolver_params.append(custom)
solver.parameters.extra_subsolvers.append("custom_no_lp_lns")
함정: 과도한 서브솔버 튜닝
Laurent Perron: "Fine-tuning such a solver is not a simple task, and often you do more harm than good by tinkering around." 기본 포트폴리오는 수년간 광범위한 벤치마킹으로 최적화된 것이다. 특수 문제 구조(예: packing + crane)가 있을 때만 커스터마이징을 시도하라.

use_lns_only

기본값: False. True로 설정하면 불완전한 LNS 휴리스틱 솔버만 실행. 최적성 보장 없음 → 반드시 max_time_in_seconds와 함께 사용. 

solver.parameters.use_lns_only = True
solver.parameters.max_time_in_seconds = 60.0  # 종료 조건 필수

3. 프리솔브

cp_model_presolve

기본값: True. 풀기 전 제약 전파·변수 도메인 축소·등가 치환 수행. 복잡한 모델에서 10~100배 이상 성능 차이를 만들 수 있다. 

solver.parameters.cp_model_presolve = False  # 비활성 (보통 권장 안 함)
solver.parameters.max_presolve_iterations = 3  # 기본값 = 3 (반복 횟수 제한)
solver.parameters.cp_model_probing_level = 1   # 0=none, 1=light, 2=aggressive
solver.parameters.presolve_probing_deterministic_time_limit = 5.0  # 초
함정: 프리솔브 비활성화 시 성능 역전
프리솔브를 끄면 디버깅 속도는 빨라지지만 실제 어려운 인스턴스에서 솔버가 수렴하지 못하는 경우가 많다. 힌트(hint) 사용 시 프리솔브가 힌트 feasibility를 손상시키는 알려진 버그가 있었음 → keep_all_feasible_solutions_in_presolve = True로 완화 가능.

4. LP 이완 & 컷

linearization_level

내부 LP relaxation의 선형화 수준. 서브솔버 이름과 직접 대응:

값서브솔버의미
0no_lpLP 완전 비활성. 순수 CP. 빠르지만 바운드 약함
1default_lp기본 LP 이완. 균형 (기본값)
2max_lp최대 LP 이완. 바운드 강함, 메모리·시간 증가
solver.parameters.linearization_level = 1  # 기본 (대부분의 경우 최적)
# max_lp는 포트폴리오에서 max_lp 서브솔버가 담당하므로
# 전역으로 2로 올리는 것보다 workers 늘려 자동 포함되게 하는 편이 낫다

symmetry_level

대칭 탐지 수준. 기본값: 1 (경량).

값동작
0대칭 탐지 비활성
1기본 (기본값)
2중간 수준 대칭 탐지
3대형 문제 강제 활성 — 단, 하드코딩된 1초 시간 제한 내에서만 실행
함정: symmetry_level=3의 함정
GitHub #4419: symmetry_level=3은 대형 모델에서 1초 결정론적 시간 제한 때문에 완전한 대칭 탐지 전에 타임아웃된다. 이 제한은 현재 설정 불가능. 특정 문제에서는 이 제한을 늘리면 solve time이 크게 줄어드는 사례가 보고됨.

5. 탐색 분기 전략

search_branching 열거형

CP-SAT의 분기 전략을 제어한다. 기본값: AUTOMATIC_SEARCH.

값Python 상수설명
0cp_model.AUTOMATIC_SEARCH자동 선택 (권장 기본값)
1cp_model.FIXED_SEARCHAddDecisionStrategy를 정확히 따름
2cp_model.PORTFOLIO_SEARCH다수 전략 포트폴리오
3cp_model.LP_SEARCHLP 이완 해 기반 분기
4cp_model.PSEUDO_COST_SEARCH의사비용 기반 (MIP 스타일)
5cp_model.PORTFOLIO_WITH_QUICK_RESTART_SEARCH포트폴리오 + 빠른 재시작
6cp_model.NO_SEARCH탐색 없음 (프리솔브만)
solver.parameters.search_branching = cp_model.AUTOMATIC_SEARCH  # 기본
solver.parameters.search_branching = cp_model.FIXED_SEARCH       # 사용자 전략 강제
solver.parameters.search_branching = cp_model.PORTFOLIO_SEARCH   # 다양성 극대화
함정: FIXED_SEARCH는 hint 없으면 위험
FIXED_SEARCH는 AddDecisionStrategy로 지정된 변수들만 순서대로 분기한다. 전략에서 누락된 변수가 있으면 탐색이 막히거나 첫 해를 못 찾는다. 반드시 모든 결정 변수를 커버하는 완전한 전략과 함께 사용하라.

6. AddDecisionStrategy

변수 선택(variable selection)과 값 선택(domain reduction)을 사용자가 직접 제어. search_branching = FIXED_SEARCH와 함께 사용해야 효력이 있다.

시그니처

model.AddDecisionStrategy(
    variables,           # List[IntVar] — 분기 변수 목록
    variable_selection,  # VariableSelectionStrategy
    domain_reduction     # DomainReductionStrategy
)

변수 선택 전략 (VariableSelectionStrategy)

상수의미
cp_model.CHOOSE_FIRST목록 순서대로 첫 번째 미결정 변수 선택 (예측 가능, 가장 빠름)
cp_model.CHOOSE_LOWEST_MIN도메인 하한이 가장 낮은 변수 선택
cp_model.CHOOSE_HIGHEST_MAX도메인 상한이 가장 높은 변수 선택
cp_model.CHOOSE_MIN_DOMAIN_SIZE도메인 크기가 가장 작은 변수 선택 (Fail-First)
cp_model.CHOOSE_MAX_DOMAIN_SIZE도메인 크기가 가장 큰 변수 선택

값(도메인) 선택 전략 (DomainReductionStrategy)

상수의미
cp_model.SELECT_MIN_VALUE도메인 최솟값 시도 (최소화 문제 기본)
cp_model.SELECT_MAX_VALUE도메인 최댓값 시도
cp_model.SELECT_LOWER_HALF하위 절반 도메인으로 분기
cp_model.SELECT_UPPER_HALF상위 절반 도메인으로 분기
cp_model.SELECT_MEDIAN_VALUE도메인 중앙값 시도

실용 예제 — 스케줄링 시작 시간 우선 결정

from ortools.sat.python import cp_model

model = cp_model.CpModel()
n_jobs = 5
starts = [model.NewIntVar(0, 1000, f"start_{i}") for i in range(n_jobs)]
ends   = [model.NewIntVar(0, 1000, f"end_{i}")   for i in range(n_jobs)]

# 시작 시간을 오름차순으로 결정 → 빠른 초기해 확보
model.AddDecisionStrategy(
    starts,
    cp_model.CHOOSE_LOWEST_MIN,   # 가장 이른 시작 가능 job 먼저
    cp_model.SELECT_MIN_VALUE     # 가능한 가장 빨리 배정
)

solver = cp_model.CpSolver()
solver.parameters.search_branching = cp_model.FIXED_SEARCH
solver.parameters.max_time_in_seconds = 60.0
status = solver.Solve(model)
print(solver.StatusName(status))

다단계 전략 (위치 → 시간 순서 보장)

# 1단계: 배정 변수 (어떤 베이에 넣을지) → CHOOSE_FIRST로 순서 고정
model.AddDecisionStrategy(
    bay_assignments,
    cp_model.CHOOSE_FIRST,
    cp_model.SELECT_MIN_VALUE
)
# 2단계: 타이밍 변수 → 배정 확정 후 최솟값 탐색
model.AddDecisionStrategy(
    start_times,
    cp_model.CHOOSE_LOWEST_MIN,
    cp_model.SELECT_MIN_VALUE
)
# 여러 AddDecisionStrategy 호출 → 앞 전략 변수가 모두 결정된 후 다음 전략 사용
Best Practice: AUTOMATIC vs FIXED
CP-SAT 자동 전략은 수년간의 벤치마킹으로 튜닝되어 있다. 도메인 지식이 있을 때만 (예: "시작 시간 먼저, 작은 값부터") FIXED를 쓴다. AUTOMATIC_SEARCH + 힌트(AddHint) 조합이 대부분의 경우 FIXED보다 낫다.

7. 결정론적 재현

random_seed

솔버 내부 난수 생성기 초기화 시드. 기본값: 1. 단일 워커(num_workers=1)에서만 완전 결정론적 재현이 보장된다. 멀티 워커는 스레드 인터리빙 때문에 결정론적이지 않다. 

# 완전 결정론적 재현 (디버깅, 논문 실험 재현)
solver.parameters.num_workers = 1
solver.parameters.random_seed = 42

# 다양한 시드로 best-of-N 앙상블
best_obj = float('inf')
best_sol = None
for seed in [1, 42, 123, 456, 789]:
    s = cp_model.CpSolver()
    s.parameters.num_workers = 4
    s.parameters.max_time_in_seconds = 30.0
    s.parameters.random_seed = seed
    status = s.Solve(model)
    if status in (cp_model.OPTIMAL, cp_model.FEASIBLE):
        if s.ObjectiveValue() < best_obj:
            best_obj = s.ObjectiveValue()
            best_sol = s
OGC 결정론화 전략
제출 전 로컬 재현을 위해 num_workers=1, random_seed=1로 한 번 실행해 솔루션 검증. 실제 서버 제출은 num_workers=4 + 고정 시드로 안정성 확보. CP-SAT 결과의 ±130K 노이즈 (메모리에서 확인)는 대부분 멀티스레드 비결정성에서 기인.

8. 로그: log_search_progress 읽기

활성화

solver.parameters.log_search_progress = True   # stdout/stderr 출력

# 커스텀 콜백으로 캡처 (파일 저장 등)
solver.log_callback = lambda msg: print(f"[CPSAT] {msg}", flush=True)
solver.parameters.log_to_stdout = False   # 콜백 전용으로 전환

로그 형식 해독

각 이벤트 행은 다음 구조를 따른다:

# 형식: EVENT | TIME | BEST_OBJ | SEARCH_RANGE | [SUBSOLVER_INFO]

#1  0.12s best:2150 next:[1800,2149] default_lp (fixed_bools=28/918)
#2  1.84s best:1890 next:[1800,1889] rins_lns_default
#Bound 8.73s best:1890 next:[1891,1890] lb_tree_search (nodes=13/18 rc=0 decisions=133)
#Model 12.4s  vars:450/918 constraints:302/1100

로그로 고원(plateau) 감지

# 고원 신호: #N 이벤트가 오랫동안 없고 #Bound 만 발생
# → incumbent 개선 없이 bound 만 좁혀지는 중
# → 만약 bound가 incumbent에 수렴하지 않으면 구조적 어려움

# 실용 패턴: best와 next 하한의 갭 추적
class GapMonitor(cp_model.CpSolverSolutionCallback):
    def on_solution_callback(self):
        gap = abs(self.objective_value - self.best_objective_bound)
        rel_gap = gap / max(1.0, abs(self.objective_value))
        print(f"t={self.wall_time:.1f}s  obj={self.objective_value:.0f}"
              f"  bound={self.best_objective_bound:.0f}  gap={rel_gap:.2%}")
로그 분석 도구
CP-SAT Primer는 Log Analyzer 도구를 권장한다: bound·gap·모델 변경을 시간 축으로 시각화. 이벤트 기반 로그를 수동으로 읽기 어려울 때 필수.

10. 완전 설정 예제 (OGC 패턴)

from ortools.sat.python import cp_model
import time

def build_solver(timelimit: float, seed: int = 1) -> cp_model.CpSolver:
    solver = cp_model.CpSolver()
    p = solver.parameters

    # ── 종료 제어 ──────────────────────────────────
    p.max_time_in_seconds   = max(1.0, timelimit - 10.0)  # 10초 reserve
    p.relative_gap_limit    = 0.0    # 갭 종료 비활성 (경쟁 상황)
    p.absolute_gap_limit    = 1e-4   # 정수 최적 수렴만

    # ── 병렬 ────────────────────────────────────────
    p.num_workers           = 4      # 평가서버 4코어
    p.interleave_search     = True   # LNS 다양성 ↑

    # ── 결정론 ──────────────────────────────────────
    p.random_seed           = seed

    # ── 프리솔브 ─────────────────────────────────────
    p.cp_model_presolve     = True
    p.max_presolve_iterations = 3

    # ── LP ──────────────────────────────────────────
    p.linearization_level   = 1      # default (max_lp는 포트폴리오에서 자동)
    p.symmetry_level        = 1      # 기본 대칭 탐지

    # ── 로그 ─────────────────────────────────────────
    p.log_search_progress   = True

    # ── 메모리 ──────────────────────────────────────
    p.max_memory_in_mb      = 12000

    return solver


# best-of-2 앙상블 (결정론적 시드 로테이션)
def solve_best_of(model, timelimit):
    results = []
    for seed in [1, 42]:
        s = build_solver(timelimit / 2, seed=seed)
        cb = cp_model.ObjectiveSolutionPrinter()
        status = s.Solve(model, cb)
        if status in (cp_model.OPTIMAL, cp_model.FEASIBLE):
            results.append((s.ObjectiveValue(), s))
    if not results:
        return None
    return min(results, key=lambda x: x[0])[1]

흔한 함정 요약

함정 1: num_workers를 무작정 크게
workers 수를 32로 올리면 각 워커가 독립 LP relaxation + 모델 복사본을 유지. 대형 모델에서 RAM이 폭발한다. 실제 코어 수 이하로 설정하고 max_memory_in_mb를 안전망으로 두어라.
함정 2: FIXED_SEARCH에서 전략 미완비
AddDecisionStrategy에 일부 변수만 포함하고 FIXED_SEARCH를 설정하면 나머지 변수가 처리 안 돼 탐색이 막힌다. 전략에 없는 변수는 AUTOMATIC으로 보완하거나, 보조 변수 전용 추가 전략을 선언하라.
함정 3: relative_gap_limit 조기종료
relative_gap_limit = 0.05는 5% 이내면 종료하므로, 큰 인스턴스에서 수십만 단위 개선 여지를 남기고 종료될 수 있다. 경쟁 상황에서는 0.0(비활성)으로 두고 시간 제한으로만 종료하라.
함정 4: 콜백이 병목이 되는 경우
log_search_progress 콜백이나 CpSolverSolutionCallback에서 무거운 연산을 하면 솔버 전체가 그 시간만큼 블록된다. Laurent Perron: "학생들이 느린 솔버 성능에 좌절했다가 콜백이 시간을 다 먹고 있었음을 발견하는 일이 흔하다."
함정 5: conda run 크래시 (OGC 전용)
4-worker CP-SAT를 conda run -n ogc2025 python ...으로 실행하면 크래시 발생. 반드시 env python을 직접 호출: C:/Users/peter/anaconda3/envs/ogc2025/python.exe src/myalgorithm.py
함정 6: 멀티 워커 = 비결정론
num_workers > 1이면 스레드 스케줄링 때문에 같은 시드로도 결과가 달라진다. 완전 재현이 필요하면 num_workers=1로 단독 실행하거나, 결과를 "최선 솔루션" 기준으로 평가하고 재현성에 집착하지 마라.
