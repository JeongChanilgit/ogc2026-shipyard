1. LNS 개념 — 왜 필요한가

CP-SAT 단독으로는 매우 큰 모델에서 제한 시간 안에 최적 해에 가까운 해를 보장하기 어렵다. 전체 변수 공간을 한꺼번에 탐색하는 것은 NP-hard 구조상 지수 폭발을 피할 수 없다. LNS(Large Neighborhood Search)는 1998년 Paul Shaw 가 VRPTW 에 처음 적용한 아이디어로, "현재 해 근방 작은 서브 문제만 반복 최적화"한다.

핵심 사이클 :

초기해 s ← 구성 알고리즘(greedy/CP-SAT 짧은 TL)
while 시간 남음:
    N ← destroy(s)        # 변수 부분집합 선택 (이웃 정의)
    s' ← repair(s, N)     # 선택된 변수만 풀고 나머지 고정 → CP-SAT re-solve
    if obj(s') < obj(s):
        s ← s'            # 개선되면 채택 (수락 기준 변형 가능)
return s
핵심 직관
이웃 크기(풀어주는 변수 수)가 클수록 개선 여지는 크지만 서브 문제가 어려워진다. 너무 작으면 정체(local optimum), 너무 크면 CP-SAT 가 서브 문제도 못 푼다. 실전 sweet spot: 전체 변수의 10~30%.

1.1 Ruin-and-Recreate / Fix-and-Optimize

Ruin-and-Recreate(Schrimpf et al., 2000): "파괴(ruin)" 단계에서 일부 할당을 제거하고, "재건(recreate)" 단계에서 탐색적으로 다시 채운다. 수락 기준으로 시뮬레이티드 어닐링을 쓰기도 한다.

Fix-and-Optimize: MIP/CP 문헌의 표준 용어. 변수를 구간별로 묶어 나머지는 현재 값으로 고정하고 해당 구간만 최적화한다. 시간창 / 기계 / 자원 구간이 자주 쓰인다.

2. CP-SAT 내장 LNS — 워커 아키텍처

num_workers ≥ 2이면 CP-SAT 는 자동으로 incomplete subsolver들을 할당한다. 워커 수에 따라 LNS 전략 수가 늘어나며, 32 워커에서 완전한 15개 full-problem subsolver가 병렬 실행된다.

2.2 워커 스케줄링 방식

CP-SAT 는 LNS 전략들을 단순 라운드로빈으로 스케줄한다. 워커가 한 iteration 을 끝내면 다음 전략 차례를 수행한다 — 이것이 로그에서 각 전략의 호출 횟수가 거의 동일하게 보이는 이유다. 더 나은 해가 발견되면 모든 워커가 즉시 새 해를 기준으로 이웃을 생성한다.

2.3 주요 파라미터

solver.parameters.max_time_in_seconds = 60.0

# 결정 변수에 LNS 집중 (힌트 변수 우선)
solver.parameters.lns_focus_on_decision_variables = True
함정: use_lns_only + 시간 제한 없음
use_lns_only = True만 설정하면 incomplete subsolver 는 종료 조건을 모르므로 무한 실행. 반드시 max_time_in_seconds나 외부 callback 으로 중단 조건을 설정하라.

3. 직접 LNS 구축 — Python 루프

CP-SAT 내장 LNS 가 도메인 지식을 활용하지 못할 때, 직접 LNS 루프를 짜면 어떤 변수를 풀지를 문제 구조에 맞게 설계할 수 있다. 핵심 아이디어: 나머지 변수를 도메인 고정(단점 도메인)으로 만들고 짧은 TL로 re-solve.

3.1 기본 LNS 한 라운드 — 변수 고정 + 힌트

import random
from ortools.sat.python import cp_model

def lns_round(original_model: cp_model.CpModel,
              all_vars: list,
              current_sol: dict,      # {var_index: value}
              free_fraction: float,
              round_time: float) -> dict | None:
    """
    LNS 한 라운드:
    1. 원본 모델을 복사
    2. free_fraction 비율의 변수는 힌트만 주고 풀어둠
    3. 나머지 변수는 현재 값으로 도메인 고정 (단점 도메인)
    4. 짧은 TL로 solve → 개선되면 반환, 아니면 None
    """
    cp = cp_model.CpModel()
    cp.CopyFrom(original_model)          # proto 수준 복사

    n = len(all_vars)
    free_count = max(1, int(n * free_fraction))
    free_set = set(random.sample(range(n), free_count))

    for i, var in enumerate(all_vars):
        val = current_sol[var.Index()]
        if i not in free_set:
            # 고정: 도메인을 [val, val] 단점으로 좁힘
            cp.add_linear_constraint(var, val, val)
        else:
            # 힌트: 풀어두되 초기값 제안
            cp.add_hint(var, val)

    solver = cp_model.CpSolver()
    solver.parameters.max_time_in_seconds = round_time
    solver.parameters.num_workers = 4
    solver.parameters.log_search_progress = False

    status = solver.Solve(cp)
    if status in (cp_model.OPTIMAL, cp_model.FEASIBLE):
        return {var.Index(): solver.Value(var) for var in all_vars}
    return None


def run_lns(model: cp_model.CpModel,
            all_vars: list,
            total_time: float,
            round_time: float = 10.0,
            free_fraction: float = 0.25) -> dict:
    """전체 LNS 루프"""
    # 초기해: 짧은 TL로 구성
    solver = cp_model.CpSolver()
    solver.parameters.max_time_in_seconds = round_time
    solver.Solve(model)
    best = {v.Index(): solver.Value(v) for v in all_vars}
    best_obj = solver.ObjectiveValue()

    import time
    t0 = time.time()
    rounds = 0
    improved = 0

    while time.time() - t0 < total_time - round_time:
        result = lns_round(model, all_vars, best, free_fraction, round_time)
        rounds += 1
        if result is not None:
            # 목적함수 재평가 필요시 직접 계산 또는 solver.ObjectiveValue() 사용
            improved += 1
            best = result

    print(f"LNS: {rounds} rounds, {improved} improvements")
    return best
도메인 고정 vs. AddHint 차이
  • 도메인 고정(add_linear_constraint(var, val, val)): 변수를 단점 도메인으로 만들어 propagation 이 즉시 제거 → 프리솔브에서 극적으로 단순화. 단, 초기해가 infeasible 이면 서브 문제도 infeasible.
  • AddHint: 값을 권고할 뿐 강제하지 않음 → feasibility 안전, 하지만 솔버가 무시할 수 있어 이웃 탐색 효과 약함.
실전 패턴: 변경 불허 변수는 고정, 자유화 변수는 힌트 제공 후 해제.

3.2 시간창 이웃 (Scheduling 전용)

스케줄링 문제에서 가장 효과적인 이웃: 특정 시간 구간 안에 속하는 작업만 릴랙스. CP-SAT 내장 SchedulingTimeWindowNeighborhoodGenerator와 동일한 원리를 직접 구현한 예: 

def time_window_neighborhood(
    jobs: list,          # (start_var, end_var, duration, bay, ...)
    current_sol: dict,
    horizon: int,
    window_size: float = 0.2    # 전체 horizon 의 20%
) -> set:
    """
    무작위 시간창 [t_lo, t_hi] 안에 시작하는 작업 인덱스 반환 (릴랙스 대상)
    """
    max_t = horizon
    win = int(max_t * window_size)
    t_lo = random.randint(0, max_t - win)
    t_hi = t_lo + win

    free = set()
    for i, (sv, ev, *_) in enumerate(jobs):
        start_val = current_sol.get(sv.Index(), 0)
        if t_lo <= start_val <= t_hi:
            free.add(i)
    return free


def time_window_lns_round(model, jobs, current_sol, horizon,
                           round_time=15.0):
    """시간창 이웃으로 한 라운드"""
    free_indices = time_window_neighborhood(jobs, current_sol, horizon)
    if not free_indices:
        return None

    cp = cp_model.CpModel()
    cp.CopyFrom(model)

    for i, (sv, ev, *_) in enumerate(jobs):
        if i not in free_indices:
            # 고정: entry = current, exit = current
            s_val = current_sol[sv.Index()]
            e_val = current_sol[ev.Index()]
            cp.add_linear_constraint(sv, s_val, s_val)
            cp.add_linear_constraint(ev, e_val, e_val)
        else:
            cp.add_hint(sv, current_sol[sv.Index()])
            cp.add_hint(ev, current_sol[ev.Index()])

    solver = cp_model.CpSolver()
    solver.parameters.max_time_in_seconds = round_time
    solver.parameters.num_workers = 2
    status = solver.Solve(cp)

    if status in (cp_model.OPTIMAL, cp_model.FEASIBLE):
        return {v.Index(): solver.Value(v)
                for sv, ev, *_ in jobs for v in (sv, ev)}
    return None

3.3 관련성 기반 이웃 (Shaw, 1998)

단순 무작위 선택 대신 서로 "관련된" 변수(같은 베이, 시간 근접, 자원 충돌)를 묶어 릴랙스하면 구조적으로 의미 있는 이웃이 된다. Shaw 의 원 논문(1998)에서 VRP에 적용한 관련성 함수: 

def relatedness(job_i, job_j, current_sol, weights=(1.0, 0.5, 0.3)):
    """
    두 작업의 관련성 점수. 낮을수록 더 관련됨.
    w1: 시간 차이, w2: 위치 차이, w3: 자원 충돌
    """
    w1, w2, w3 = weights
    dt = abs(current_sol[job_i.start] - current_sol[job_j.start])
    db = 0 if job_i.bay == job_j.bay else 1
    dc = 1 if jobs_may_conflict(job_i, job_j, current_sol) else 0
    return w1 * dt + w2 * db * 100 + w3 * dc * 50


def shaw_destroy(jobs, current_sol, destroy_count=5):
    """Shaw ruin: 첫 번째 작업 무작위 선택 후 가장 관련된 destroy_count 개 릴랙스"""
    seed = random.choice(range(len(jobs)))
    scores = [(relatedness(jobs[seed], jobs[j], current_sol), j)
              for j in range(len(jobs)) if j != seed]
    scores.sort()
    return {seed} | {j for _, j in scores[:destroy_count - 1]}

4. ALNS — 적응형 LNS (Ropke & Pisinger, 2006)

Adaptive LNS는 여러 destroy/repair 연산자를 포트폴리오로 유지하고, 과거 성능(개선 빈도)에 비례해 선택 확률을 동적으로 조정한다. Ropke & Pisinger(2006)의 원 VRPTW 논문에서 검증됐으며, 현재는 스케줄링·패킹·라우팅 전반에 표준. 

import numpy as np

class ALNS:
    def __init__(self, operators: list[callable],
                 decay: float = 0.8,
                 scores: tuple = (33, 9, 13, 0)):
        """
        operators: [(destroy_fn, repair_fn), ...]
        decay: 가중치 감쇠 계수 (0 < decay < 1)
        scores: (best_new, better, accepted, rejected) 점수
        """
        self.ops = operators
        self.decay = decay
        self.reward_scores = scores
        self.weights = np.ones(len(operators))
        self.counts = np.zeros(len(operators))
        self.total_rewards = np.zeros(len(operators))

    def select_operator(self) -> int:
        probs = self.weights / self.weights.sum()
        return np.random.choice(len(self.ops), p=probs)

    def update(self, op_idx: int, reward_type: int):
        """reward_type: 0=best_new, 1=better, 2=accepted, 3=rejected"""
        r = self.reward_scores[reward_type]
        self.counts[op_idx] += 1
        self.total_rewards[op_idx] += r
        # 가중치 업데이트 (지수 이동 평균)
        self.weights[op_idx] = (
            self.decay * self.weights[op_idx] +
            (1 - self.decay) * r
        )

    def run(self, model, initial_sol, total_time, round_time=10.0):
        import time
        best = current = initial_sol
        best_obj = evaluate(best)     # 목적함수 계산 함수 필요
        t0 = time.time()

        while time.time() - t0 < total_time - round_time:
            op_idx = self.select_operator()
            destroy_fn, repair_fn = self.ops[op_idx]

            partial = destroy_fn(current)
            new_sol = repair_fn(model, partial, round_time)

            if new_sol is None:
                self.update(op_idx, 3)    # rejected
                continue

            new_obj = evaluate(new_sol)
            if new_obj < best_obj:
                best, best_obj = new_sol, new_obj
                self.update(op_idx, 0)    # best_new
                current = new_sol
            elif new_obj < evaluate(current):
                self.update(op_idx, 1)    # better
                current = new_sol
            else:
                self.update(op_idx, 3)    # rejected

        return best
ALNS 탐색-활용 트레이드오프
초기에는 모든 연산자를 균등하게 탐색하다가, 잘 동작하는 연산자에 가중치가 집중된다. decay=0.8은 과거 성능을 80% 유지 + 최근 성과 20% 반영. 긴 런에서는 낮춰라. OR-Tools 내장 WeightedRandomRelaxationNeighborhoodGenerator가 이 원리를 구현한다.

5. Rolling Horizon — 시간축 분해

Rolling Horizon(슬라이딩 윈도우)은 긴 시간축 스케줄링 문제를 겹쳐지는(overlapping) 작은 시간창으로 잘라 순차 최적화한다. 각 창은 CP-SAT 서브 문제로 풀고, 창이 앞으로 이동하면서 확정된 결정은 고정한다.

5.1 알고리즘 구조

def rolling_horizon(
    jobs: list,
    horizon: int,
    window: int,          # 한 창의 크기 (시간 단위)
    step: int,            # 창 이동 거리 (step <= window → 오버랩)
    overlap: int,         # 다음 창과 겹치는 구간 (경계 유연성)
    round_tl: float = 30.0
) -> dict:
    """
    Rolling Horizon 스케줄링.
    Parameters:
        window: H (planning horizon size)
        step:   S (execution step, S <= H)
        overlap: 인접 창 간 공유 작업 수
    """
    solution = {}          # 확정 결정 저장
    frozen = set()         # 이미 고정된 작업 집합

    t = 0
    while t < horizon:
        t_lo, t_hi = t, t + window

        # 현 창에 속하는 작업 분류
        in_window = [j for j in jobs
                     if job_release(j) < t_hi and job_due(j) > t_lo]
        commit = [j for j in in_window
                  if job_due(j) <= t_lo + step]   # 이 창에서 확정할 작업
        boundary = [j for j in in_window
                    if j not in commit]             # 다음 창으로 넘길 작업

        # 서브 문제 생성: frozen 작업은 고정, 나머지는 자유
        sub_sol = solve_subproblem(
            jobs=in_window,
            fixed={j: solution[j] for j in in_window if j in frozen},
            round_tl=round_tl
        )

        # commit 작업 결정 확정
        for j in commit:
            solution[j] = sub_sol[j]
            frozen.add(j)

        # boundary 작업에 힌트 제공 (다음 창의 초기해)
        for j in boundary:
            solution[j] = sub_sol[j]   # 힌트용 (아직 미확정)

        t += step

    return solution


def solve_subproblem(jobs, fixed: dict, round_tl: float) -> dict:
    """단일 시간창 서브 문제를 CP-SAT 로 풀기"""
    model = cp_model.CpModel()
    vars_ = {}
    for j in jobs:
        start = model.new_int_var(j.release, j.due - j.duration, f"s_{j.id}")
        end = model.new_int_var(j.release + j.duration, j.due, f"e_{j.id}")
        iv = model.new_interval_var(start, j.duration, end, f"iv_{j.id}")
        vars_[j.id] = (start, end, iv)

    # 고정된 작업: 도메인 단점으로 축소
    for j, sol in fixed.items():
        s, e, _ = vars_[j.id]
        model.add_linear_constraint(s, sol["start"], sol["start"])
        model.add_linear_constraint(e, sol["end"], sol["end"])

    # NoOverlap
    model.add_no_overlap([iv for _, _, iv in vars_.values()])

    # 목적: tardiness 최소화
    tardiness = []
    for j in jobs:
        s, e, _ = vars_[j.id]
        tard = model.new_int_var(0, j.due * 2, f"tard_{j.id}")
        model.add_max_equality(tard, [0, e - j.due])
        tardiness.append(j.weight * tard)
    model.minimize(sum(tardiness))

    solver = cp_model.CpSolver()
    solver.parameters.max_time_in_seconds = round_tl
    solver.parameters.num_workers = 4
    solver.Solve(model)

    return {j.id: {"start": solver.Value(vars_[j.id][0]),
                   "end":   solver.Value(vars_[j.id][1])}
            for j in jobs}
함정: 경계 작업 일관성 깨짐
step = window(오버랩 없음)이면 이전 창에서 확정된 작업이 다음 창의 feasibility 를 막을 수 있다. 해결책: overlap > 0으로 경계에 여유 구간을 두거나, 경계 작업을 "소프트 고정"(힌트+범위 완화)으로 처리하라.
Rolling Horizon 핵심 파라미터
  • H (window): 클수록 품질 ↑, 서브 문제 어려움 ↑
  • S (step): S ≤ H/2 권장 (충분한 오버랩으로 경계 효과 완화)
  • T (round TL): 서브 문제당 허용 시간; 전체 TL / 창 수에 맞게
  • 오버랩 비율: (H−S)/H ≈ 30~50% 가 실전 sweet spot

6. 구역 분해 — Per-Bay / Per-Resource Fix-and-Optimize

시간축이 아닌 자원(베이·기계·구역) 축으로 분해한다. 전역 배정(어떤 블록이 어느 베이에 가는가)을 고정하고, 베이별로 독립된 CP-SAT 서브 문제(타이밍·배치)를 순차 또는 병렬로 푼다.

6.1 Per-Bay 분해 패턴

def solve_per_bay(assignment: dict,    # {block_id: bay_id}
                  blocks: list,
                  bays: list,
                  global_timelimit: float) -> dict:
    """
    전역 배정이 고정됐다고 가정 → 베이별 독립 CP-SAT 타이밍 오라클.
    병렬 실행 가능 (베이 간 간섭 없을 때).
    """
    import concurrent.futures

    per_bay_blocks = {b.id: [] for b in bays}
    for blk in blocks:
        bay_id = assignment[blk.id]
        per_bay_blocks[bay_id].append(blk)

    per_bay_tl = global_timelimit / len(bays) * 1.5   # 여유 계수

    def solve_one_bay(bay_id):
        bay_blocks = per_bay_blocks[bay_id]
        if not bay_blocks:
            return bay_id, {}
        return bay_id, _cpsat_bay_timing(bay_blocks, per_bay_tl)

    solution = {}
    with concurrent.futures.ThreadPoolExecutor(max_workers=4) as executor:
        futures = {executor.submit(solve_one_bay, b.id): b.id for b in bays}
        for fut in concurrent.futures.as_completed(futures):
            bay_id, bay_sol = fut.result()
            solution.update(bay_sol)

    return solution


def _cpsat_bay_timing(blocks: list, timelimit: float) -> dict:
    """단일 베이의 타이밍(entry/exit) 최적화 — NoOverlap + 크레인 제약"""
    model = cp_model.CpModel()
    horizon = max(b.due for b in blocks) + 1

    intervals, starts, ends = [], [], []
    for b in blocks:
        s = model.new_int_var(b.release, horizon, f"s_{b.id}")
        e = model.new_int_var(b.release + b.duration, horizon, f"e_{b.id}")
        iv = model.new_interval_var(s, b.duration, e, f"iv_{b.id}")
        starts.append(s); ends.append(e); intervals.append(iv)

    # NoOverlap (같은 베이 내 물리 공간 충돌 — 여기선 시간 충돌로 단순화)
    model.add_no_overlap(intervals)

    # 크레인 j >= k 제약: 위 레이어가 먼저 OUT 되어야 아래 레이어 IN 가능
    for i, bi in enumerate(blocks):
        for j, bj in enumerate(blocks):
            if i != j and bi.layer > bj.layer and bi.bay_zone == bj.bay_zone:
                # bi 가 위에 있으면 bi.exit <= bj.entry
                model.add(ends[i] <= starts[j])

    # 목적: tardiness
    tardiness_terms = []
    for i, b in enumerate(blocks):
        t = model.new_int_var(0, horizon, f"t_{b.id}")
        model.add_max_equality(t, [0, ends[i] - b.due])
        tardiness_terms.append(b.weight * t)
    model.minimize(sum(tardiness_terms))

    solver = cp_model.CpSolver()
    solver.parameters.max_time_in_seconds = timelimit
    solver.parameters.num_workers = 2
    status = solver.Solve(model)

    if status in (cp_model.OPTIMAL, cp_model.FEASIBLE):
        return {b.id: {"entry": solver.Value(starts[i]),
                       "exit":  solver.Value(ends[i])}
                for i, b in enumerate(blocks)}
    # fallback: EDD 정렬
    return edd_fallback(blocks)
Per-Bay 분해의 장점
  • 베이 간 간섭이 없으면 완전 병렬화 가능
  • 각 서브 문제 크기 O(블록/베이) → 전체 문제보다 지수적으로 쉬움
  • 전역 배정 품질이 병목 → LNS/재배정과 반복 조합 가능
함정: 부분 고정으로 feasibility 파괴
전역 배정을 고정한 채 베이별 타이밍을 풀 때, 특정 베이에 블록이 과잉 배정되면 그 베이 서브 문제가 infeasible이 된다. 대응: (1) 배정 단계에서 베이 용량 제약 엄격히 적용, (2) infeasible 감지 시 해당 베이 일부 블록을 강제로 다른 베이로 이동(repair), (3) per-bay 문제마다 try/except + fallback 해를 준비.

7. 큰 모델에서 단일 solve 가 안 끝날 때의 전략

7.1 전략 선택 플로우차트

증상진단권장 전략
초기해조차 못 찾음 feasibility pump 가 막힘, 모델이 과제약 제약 완화, use_lns_only=False로 완전 탐색 유지
초기해는 있지만 개선 없음 LNS 이웃이 너무 작거나 구조 부적합 직접 LNS (이웃 크기↑), ALNS, 시간창 이웃
시간이 지나도 plateau 로컬 옵티멈 갇힘 큰 이웃 LNS(20~40%), 다른 이웃 타입, SA 수락 기준
메모리/시간 폭발 전체 모델이 너무 큼 Rolling Horizon 또는 Per-Resource 분해
베이별 결과가 나쁨 전역 배정이 나빠서 per-bay 풀이에 한계 배정 재최적화 + per-bay LNS 조합

7.2 실전 권장 조합

# 권장 구성: 구성 → 내장 LNS → 직접 LNS → per-bay 정제
def full_pipeline(prob_info, timelimit):
    T = timelimit
    T_construct = min(30, T * 0.15)
    T_cpsat_lns = min(60, T * 0.30)
    T_direct_lns = T - T_construct - T_cpsat_lns - 10

    # 1단계: 빠른 greedy 초기해
    sol = greedy_construct(prob_info)

    # 2단계: CP-SAT 내장 LNS (워커 많을수록 좋음)
    solver = cp_model.CpSolver()
    solver.parameters.num_workers = 4
    solver.parameters.max_time_in_seconds = T_cpsat_lns
    # (full model solve with warm hint)
    for v, val in sol.items():
        model.add_hint(v, val)
    status = solver.Solve(model)
    if status in (cp_model.OPTIMAL, cp_model.FEASIBLE):
        sol = extract_solution(solver)

    # 3단계: 직접 LNS (혼잡 베이 타이밍 집중)
    congested_bays = identify_congested_bays(sol, prob_info)
    for bay in congested_bays:
        if time_remaining() < 10:
            break
        improved = time_window_lns_round(
            model=bay_model(bay, sol),
            jobs=bay_blocks(bay, prob_info),
            current_sol=sol,
            horizon=prob_info["horizon"],
            round_time=min(15, time_remaining() * 0.3)
        )
        if improved:
            sol.update(improved)

    return sol

8. 흔한 함정

이웃이 너무 크면 서브 문제도 못 풀린다
free_fraction 을 50% 이상으로 올리면 서브 문제가 원 문제와 거의 같은 크기가 되어 round_time 안에 좋은 해를 못 찾는다. 권장 범위: 10~30%. 작게 시작해서 plateau 시 늘려라.
부분 고정 시 feasibility 파괴
이전 라운드 해를 고정할 때 제약 위반이 있으면 서브 문제 자체가 infeasible 이 된다. 항상 고정 전에 check_feasibility(sol)로 현재 해가 feasible 임을 확인. 또는 고정 대신 강한 페널티로 부드럽게 유도하라.
Rolling Horizon 에서 경계 블록 inconsistency
창이 이동할 때 경계에 있는 작업의 결정이 이전 창과 다음 창에서 충돌할 수 있다. 해결: 경계 구간(overlap zone)의 작업은 미확정으로 두고 다음 창에서 재최적화. commit 은 창의 앞 S 단위만.
model.CopyFrom 비용 과소평가
매 LNS 라운드마다 큰 모델을 proto 복사하면 CPU 시간이 상당히 소모된다. 대안: 고정 제약을 가정(assumption)으로 추가 → SolveWithAssumptions 또는 CpModel 에 AddAssumptions로 Boolean 리터럴 가정 후 재solve. 단, 이 방법은 변수 도메인이 아닌 Boolean 고정에만 적용 가능.
단일 이웃 전략 고집 → 편향된 탐색
시간창 이웃만 쓰면 창 경계 밖의 구조적 문제를 못 고친다. ALNS 처럼 여러 이웃 타입(시간창, 자원창, 무작위, 관련성)을 조합하면 다양한 구조를 탐색할 수 있다.
per-bay 병렬 CP-SAT 에서 CP-SAT 자체가 멀티스레드
num_workers=4 per-bay 서브 문제를 4개 병렬 실행하면 실제로 4×4=16개 스레드가 동시 실행된다. CPU 코어 수를 초과하면 컨텍스트 스위치 오버헤드로 역효과. per-bay 병렬 시 각 bay solver 의 num_workers=1~2로 제한하라.
