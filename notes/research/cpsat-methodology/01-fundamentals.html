CP-SAT Methodology · Chapter 01

CP-SAT 작동원리 & 아키텍처

Google OR-Tools의 CP-SAT는 SAT 기반 Constraint Programming 솔버다. Lazy Clause Generation(LCG), LP relaxation, 병렬 포트폴리오, 완전 정수 도메인을 결합해 MiniZinc Challenge 2024 전 부문 금메달을 석권했다. 이 페이지는 솔버의 내부 구조를 단계별로 해부한다.

OGC 2026 — 조선소 블록 배치 관련성

OGC 2026 문제는 2D 이형 폴리곤 패킹 + 단일머신 지연(tardiness) 최소화 + 베이 배정 + 크레인 수직접근(j ≥ k) 제약이 결합된 NP-hard 복합 문제다. 평가 서버 환경(4 CPU 코어, 16 GB, 수 분~30분 벽시계)은 CP-SAT의 병렬 포트폴리오가 직접 매핑되는 환경이다.

  • 타이밍 서브문제: 위치를 고정한 뒤 블록별 ENTRY/EXIT 시각을 최적화하는 1-D 비겹침 스케줄링 문제는 CP-SAT NoOverlap + IntervalVar로 정확하게 표현되며, LP relaxation이 bounds를 빠르게 조인다.
  • 크레인 제약(j ≥ k): 동일 베이 내 스택된 블록은 위에 있는 블록이 먼저 출고되어야 한다는 우선순위 제약 — CP-SAT의 precedence constraint(model.Add(exit_j <= entry_k))로 정확히 모델링 가능하다.
  • 4-코어 병렬 활용: solver.parameters.num_workers = 4로 설정하면 CP search / LP / LNS 워커를 동시 활용한다. src/baypack_cp.py의 per-bay CP-SAT timing oracle이 이 구조다.
  • 정수 스케일링: 시각(부동소수)을 분 또는 초 단위 정수로 미리 변환해야 CP-SAT 도메인에 입력 가능하다.

1. CP-SAT란 무엇인가

CP-SAT는 Constraint Programming(CP)과 Boolean SAT solver를 융합한 하이브리드 최적화 엔진이다. 2011년 Laurent Perron(Google)이 OR-Tools의 일부로 개발했으며, 2017년부터 MiniZinc Challenge에서 최상위권을 유지하고 있다. 2024년에는 Fixed / Free / Parallel / Open / Local Search 전 부문에서 금메달을 획득했다.

LAYER 01

SAT Core (CDCL)

Boolean Conflict-Driven Clause Learning. 충돌 분석을 통해 학습된 절(clause)을 축적하며 탐색 공간을 지수적으로 줄인다.

LAYER 02

CP Propagators

도메인 기반 제약 전파기(NoOverlap, Cumulative, AllDiff, Circuit…). 각 전파기는 SAT core에 설명 절(explanation clause)을 제공한다.

LAYER 03

LP Relaxation (GLOP)

선형 완화 + cutting plane. 정수 최적값의 lower bound를 강화하고, reduced cost fixing으로 변수 도메인을 축소한다.

LAYER 04

LNS / ViolationLS

Large Neighborhood Search와 위반 기반 로컬 서치. 현재 최적해를 부분적으로 해제하고 재최적화해 빠른 개선을 이끈다.

고전 CP / MIP과의 차이

관점고전 CP고전 MIPCP-SAT

경계 개선 제약 전파만 LP relaxation 중심 LCG 절 학습 + LP 동시

스케줄링 NoOverlap 전통적 강점 Disjunctive 모델 번잡 IntervalVar + NoOverlap 최적화

2. Lazy Clause Generation (LCG)

LCG는 Peter Stuckey(호주 Melbourne 대학)가 제안한 핵심 기법이다. CP-SAT 마스코트가 오리너구리(platypus)인 이유가 바로 호주 출신 기술이기 때문이다.

2.1 Integer Variable의 Boolean 인코딩

CP-SAT는 모든 정수 변수 x ∈ [lb, ub]를 내부적으로 두 종류의 Boolean 리터럴로 인코딩한다:

  • [x == v] — x가 정확히 v인가
  • [x ≤ v] — x가 v 이하인가

이 인코딩 덕분에 CP 전파기가 생성하는 도메인 축소를 SAT 절(clause)로 자연스럽게 표현할 수 있다.

2.2 전파기의 설명 절 (Explanation Clause)

CP-SAT의 각 전파기(예: NoOverlap)는 왜 도메인을 축소했는지 설명(explanation)을 SAT core에 제공한다. 예를 들어 [x ≤ 2]와 x ≥ y 제약이 있으면, 전파기는 다음 절을 생성한다: 

[x ≤ 2] → [y ≤ 2]

이 절은 SAT core의 절 데이터베이스에 추가된다. 이후 동일하거나 유사한 부분 배정이 나타나면 SAT engine이 CP 전파기를 다시 호출하지 않고도 즉시 추론할 수 있다. 이것이 "Lazy"한 이유 — 클라우즈가 필요할 때만 생성된다.

2.3 CDCL과의 결합

LCG는 SAT solver의 CDCL(Conflict-Driven Clause Learning) 루프 안에서 동작한다. 충돌이 발생하면 CDCL은 설명 절들을 역추적하여 충돌 절(conflict clause)을 학습하고, 비연대적 역추적(non-chronological backjumping)으로 탐색을 효율화한다. CP-SAT는 SAT VSIDS 휴리스틱으로 Boolean 변수 선택 순서를 결정하며, 정수 변수 탐색(분기 방향 결정)은 그 위에서 별도의 CP 탐색 휴리스틱이 담당한다.

핵심 직관

LCG는 "CP 전파기가 SAT 증명기에게 논리적 의미를 설명해 주는 번역기"다. 덕분에 CP 솔버가 오랫동안 약했던 lower bound 개선 능력을 SAT의 절 학습이 보완한다. 이것이 CP-SAT가 단순 CP보다 탐색 노드를 1~2 자릿수 수준으로 줄이는 원리다.

3. 병렬 워커 포트폴리오

CP-SAT는 num_workers 파라미터로 병렬 워커 수를 제어하는 포트폴리오 솔버다. 워커는 서로 독립적으로 동작하지만 공유 메모리를 통해 정보를 교환한다. 솔루션의 어떤 부분도 워커 간에 분할하지 않는다 — 각 워커는 전체 문제 공간을 탐색한다.

3.2 워커 간 정보 공유 메커니즘

워커들은 공유 메모리의 세 채널을 통해 실시간으로 정보를 교환한다:

  • SharedClausesManager: 학습된 Boolean 절(clause)을 공유. 한 워커의 충돌 학습이 다른 워커의 탐색을 즉시 가속.
  • Integer Bound Updates: 어느 워커든 변수 bound를 좁히면 전체 워커에 전파. 강력한 도메인 축소.
  • Solution Incumbents: 가능해를 발견하면 전체 워커의 upper bound가 갱신. branch-and-bound pruning 효과 공유.
워커 수 지침 (OGC 서버 기준: 4코어)

num_workers = 4 설정 시: 워커 2개부터 LNS(heuristic)가 활성화, 5개부터 first-solution solver 별도 추가. 4코어 환경에서는 default_lp + no_lp + LNS 2개가 균형 잡힌 포트폴리오를 형성한다. OGC 2026 타이밍 oracle에서는 num_workers = 4가 실제 측정 최적값이었다.

3.3 워커 수에 따른 활성 솔버 변화

# num_workers에 따라 활성 워커가 달라진다
from ortools.sat.python import cp_model

solver = cp_model.CpSolver()
solver.parameters.num_workers = 4  # OGC 서버 = 4코어

# 1 worker  : default_lp 단독 (LP+LCG)
# 2 workers : + LNS 워커 1개 추가
# 5 workers : + first-solution 전용 워커
# 8 workers : + core, max_lp, lb_tree_search 등 추가
# 32 workers: 전체 15개 full subsolver 모두 활성

4. Presolve

CP-SAT는 실제 탐색 전에 CpModelPresolver를 통한 강력한 사전 단순화를 수행한다. Presolve는 cp_model_presolve = true(기본값)로 항상 활성화된다.

4.1 주요 Presolve 단계

  1. 도메인 축소: 제약 전파로 변수 도메인 초기 축소. [x ∈ [0,10]]가 [x ∈ [3,7]]로 줄어들 수 있음.
  2. 변수 대체 (Variable Substitution): y = 2x + 3 형태의 어파인 관계를 발견하면 변수 하나를 제거.
  3. 제약 단순화: 자동 참(tautology) 또는 도메인 내 항등 제약 제거.
  4. Probing: Boolean 변수를 0 또는 1로 임시 고정 후 전파. 묵시적 implication을 발견.
  5. 이중(Dual) 감소: 목적함수 관점에서 단방향으로만 영향을 주는 변수를 최적화 방향으로 고정.
  6. SAT Presolve: cp_model_use_sat_presolve = true로 SAT-level simplification 추가 적용.
Presolve 함정: 변수가 사라질 수 있다

Presolve 후 원래 모델의 변수가 내부적으로 병합/제거될 수 있다. AddHint(var, value)를 사용할 때 presolve 이후에 해당 변수가 제거되면 힌트가 소리 없이 무시된다. 힌트가 전체 변수 커버리지를 갖추지 못하거나 presolve와 충돌하면 효과가 없다.

4.2 Presolve 설정

solver.parameters.cp_model_presolve = True         # 기본값, 항상 켜두기
solver.parameters.cp_model_use_sat_presolve = True  # SAT 레벨 단순화
solver.parameters.max_presolve_iterations = 3       # 반복 횟수 (기본 3)
solver.parameters.use_sat_inprocessing = True       # 재시작 시점 인처리

5. LP Relaxation & Cut 생성

CP-SAT 2023년부터 CP-SAT-LP라는 이름으로 LP 통합이 공식화됐다 (Laurent Perron & Frédéric Didier, CP 2023). 내부 LP 솔버는 Google의 GLOP이다.

5.1 LP가 하는 일

  • Lower bound 강화: 정수 제약을 완화한 연속 LP를 풀어 목적함수 하한을 얻는다.
  • Cut 생성: CutGenerator 클래스들이 다양한 cutting plane(Chvátal-Gomory, Lift-and-project, Cover cut 등)을 생성해 LP polyhedron을 정수 hull에 근접시킨다.
  • Reduced Cost Fixing: LP reduced cost를 이용해 특정 값이 최적해에 등장할 수 없음을 증명하고 도메인을 줄인다.
  • Branch 가이드: LP 분수해를 분기점 선택의 힌트로 사용.

5.2 linearization_level 설정

solver.parameters.linearization_level = 1   # 0=LP 없음, 1=기본(default), 2=최대
# max_lp 워커는 linearization_level=2로 자동 설정됨
# 스케줄링 문제에서는 level=2가 z1 lower bound를 크게 강화한다

6. 정수 전용 도메인 & 스케일링

CP-SAT는 부동소수점 변수를 지원하지 않는다. 모든 변수는 64비트 정수(int64)여야 하며, 실수 계수나 상수는 반드시 사전에 정수로 스케일링해야 한다.

6.1 스케일링 패턴

from ortools.sat.python import cp_model

SCALE = 1000  # 소수점 3자리 → 정수 변환

model = cp_model.CpModel()

# 실수 계수 0.5를 정수 계수 500 (SCALE 적용)으로 변환
x = model.new_int_var(0, 10 * SCALE, 'x')
y = model.new_int_var(0, 10 * SCALE, 'y')

# 0.5*x + 1.5*y <= 8.0  →  500*x + 1500*y <= 8000
model.add(500 * x + 1500 * y <= 8 * SCALE)

# OGC: 시각은 분 단위 정수 → 직접 사용 가능
entry = model.new_int_var(0, 10000, 'entry_time')  # 분 단위
오버플로우 함정: SCALE 크기 주의

변수 도메인 최대값 × SCALE이 int64 범위(~9.2 × 10¹⁸)를 넘으면 안 된다. 또한 제약 계수끼리 곱해지는 경우(빅-M 표현 등)도 오버플로우 위험이 있다. CP-SAT는 입력 시 MODEL_INVALID로 이를 탐지하지만, 조용히 잘못된 결과를 내는 경우도 있으므로 최대 도메인 × 최대 계수 < 10¹⁵를 실용 가이드라인으로 삼는다.

7. 결과 상태 코드 & 최적성 증명

solver.Solve(model)는 다섯 가지 상태 중 하나를 반환한다. 

from ortools.sat.python import cp_model

model = cp_model.CpModel()
solver = cp_model.CpSolver()

# ... 모델 구성 ...

status = solver.Solve(model)

if status == cp_model.OPTIMAL:
    print(f"최적해 확정: {solver.objective_value}")
    print(f"  → lower bound = upper bound = {solver.best_objective_bound}")
elif status == cp_model.FEASIBLE:
    gap = abs(solver.objective_value - solver.best_objective_bound)
    rel_gap = gap / max(1e-10, abs(solver.objective_value))
    print(f"실현가능해 (gap {rel_gap:.2%}): {solver.objective_value}")
    print(f"  proven bound: {solver.best_objective_bound}")
elif status == cp_model.INFEASIBLE:
    print("제약을 만족하는 해 없음 (증명됨)")
elif status == cp_model.MODEL_INVALID:
    print("모델 오류:", model.validate())  # 오류 메시지 출력
elif status == cp_model.UNKNOWN:
    print("시간/자원 초과 — 해 미발견, 하한도 미개선")

7.1 상태별 의미

상태의미OGC 대응
OPTIMAL 최적해 발견 + 최적성 증명 완료. objective_value == best_objective_bound 타이밍 oracle이 per-bay 최적 보장
FEASIBLE 가능해 존재, 최적성 미증명. gap = (obj − bound)/obj 확인 필요 시간 제한 내 최선해 채택
INFEASIBLE 모든 제약을 동시에 만족하는 배정 없음. 모델 검토 필요 크레인/베이 제약 과도 → 완화 필요
MODEL_INVALID 정수 오버플로우, 미정의 변수 참조 등 모델 에러 model.validate()로 즉시 진단
UNKNOWN 시간/메모리 한계 도달. 가능해도 하한도 없음 타임아웃 — 베이스라인 해 사용

7.2 Gap과 best_objective_bound

CP-SAT는 탐색 중 항상 두 가지 경계를 유지한다:

  • Upper Bound (incumbent): 지금까지 발견된 최선 가능해의 목적함수 값
  • Lower Bound (best_objective_bound): LP relaxation + 절 학습으로 증명된 최소 목적함수 값

두 경계가 수렴하면 OPTIMAL이 선언된다. Gap = (UB − LB) / UB × 100%가 작을수록 현재 해가 최적에 가깝다.

로그에서 Gap 읽기

CP-SAT 로그에는 best:XXX next:[LB, UB] 형태로 현재 상태가 출력된다. best는 최선 incumbent, next의 범위가 좁아질수록 최적성에 근접. solver.parameters.log_search_progress = True로 활성화 가능.

8. 결정론(Determinism)

CP-SAT는 기본적으로 비결정론적이다 — 같은 문제를 두 번 실행해도 동일한 해를 보장하지 않는다. 이는 병렬 워커 간 타이밍 경쟁, 운영체제 스케줄링 등의 영향을 받기 때문이다.

8.1 결정론 강제 방법

solver.parameters.random_seed = 42         # 동일 시드로 재현성 향상 (완전 보장 아님)
solver.parameters.num_workers = 1          # 단일 워커 → 실질적 결정론 (속도 희생)
solver.parameters.max_deterministic_time = 60.0  # 결정론적 시간 한계
solver.parameters.interleave_search = True # 다양한 전략을 결정론적 방식으로 인터리빙
OGC 시사점: CP-SAT 노이즈 ±130K

OGC 2026 세션 기록에 따르면 CP-SAT 결과의 변동폭이 ±130K에 달한다. 비교 실험은 반드시 동일 시드 + 동일 워커 수로 paired 테스트(×2 이상)를 수행해야 한다. random_seed만으로는 병렬 환경에서 완전한 결정론이 보장되지 않는다.

10. 기본 API 사용 패턴

ortools.sat.python.cp_model 모듈의 핵심 API 관용구를 정리한다. API

10.1 최소 작동 예제

from ortools.sat.python import cp_model

model = cp_model.CpModel()
solver = cp_model.CpSolver()

# 변수 선언
x = model.new_int_var(0, 100, 'x')
y = model.new_int_var(0, 100, 'y')

# 제약
model.add(x + y <= 50)
model.add(x >= 10)

# 목적함수 (최소화)
model.minimize(3 * x + 2 * y)

# 파라미터 설정
solver.parameters.max_time_in_seconds = 30.0
solver.parameters.num_workers = 4
solver.parameters.log_search_progress = True

# 풀기
status = solver.Solve(model)

if status in (cp_model.OPTIMAL, cp_model.FEASIBLE):
    print(f"x={solver.value(x)}, y={solver.value(y)}")
    print(f"obj={solver.objective_value:.1f}, bound={solver.best_objective_bound:.1f}")
    gap_pct = (solver.objective_value - solver.best_objective_bound) / max(1e-9, solver.objective_value) * 100
    print(f"gap={gap_pct:.2f}%")

10.2 Boolean 변수와 리파이케이션

# Boolean 변수
b = model.new_bool_var('active')

# OnlyEnforceIf: 조건부 제약 (Big-M 없이!)
model.add(x >= 20).only_enforce_if(b)
model.add(x <= 5).only_enforce_if(b.negated())

# Boolean 표현식
model.add_bool_or([b, model.new_bool_var('c')])  # b OR c
model.add_bool_and([b])                           # b가 True여야 함

# 변수값을 bool로 참조
model.add(b == 1).only_enforce_if(x > 0)  # 주의: CP-SAT는 이 구문 미지원 → intermediate var 사용

10.3 스케줄링 인터벌 변수 (OGC 핵심)

# OGC 베이 타이밍 모델 예시
blocks = ['B1', 'B2', 'B3']
ready = {'B1': 10, 'B2': 0, 'B3': 25}   # R_i: 최조 ENTRY 가능 시각
proc  = {'B1': 15, 'B2': 20, 'B3': 10}  # P_i: 최소 작업 기간
due   = {'B1': 30, 'B2': 50, 'B3': 40}  # D_i: 마감
HORIZON = 200

model = cp_model.CpModel()

entry, exit_, tardiness, intervals = {}, {}, {}, {}
for b in blocks:
    entry[b] = model.new_int_var(ready[b], HORIZON, f'entry_{b}')
    exit_[b] = model.new_int_var(ready[b] + proc[b], HORIZON, f'exit_{b}')
    dur      = model.new_int_var(proc[b], HORIZON, f'dur_{b}')
    intervals[b] = model.new_interval_var(entry[b], dur, exit_[b], f'iv_{b}')

    # P_i 보장: EXIT - ENTRY >= P_i
    model.add(exit_[b] - entry[b] >= proc[b])

    # tardiness = max(0, EXIT - D_i)
    tardiness[b] = model.new_int_var(0, HORIZON, f'tard_{b}')
    model.add_max_equality(tardiness[b], [exit_[b] - due[b], model.new_constant(0)])

# NoOverlap: 동일 베이에서 블록 겹침 금지
model.add_no_overlap(list(intervals.values()))

# 크레인 j>=k 예시: B1이 B3 위에 있으면 B1 먼저 출고
model.add(exit_['B1'] <= entry['B3'])   # B3는 B1 출고 후 입고

model.minimize(sum(tardiness.values()))

solver = cp_model.CpSolver()
solver.parameters.num_workers = 4
solver.parameters.max_time_in_seconds = 30.0
status = solver.Solve(model)

흔한 함정 (Anti-Patterns)

안티패턴 1: 부동소수 변수 직접 사용

model.new_int_var(0, 1.5, 'x') — CP-SAT는 부동소수 도메인을 허용하지 않는다. 실수 계수가 필요하면 미리 정수로 스케일링해야 한다. 묵시적 형변환 없이 MODEL_INVALID가 반환된다.

안티패턴 2: Big-M 과도 사용

model.add(x <= M * b) 형태의 Big-M은 LP relaxation을 크게 약화시킨다. M이 크면 LP bound가 의미 없어지고 branch-and-bound가 폭발한다. 대신 only_enforce_if(b)를 사용하거나, 도메인 구간을 직접 설정해 M을 최소화한다.

안티패턴 3: num_workers = 1 고집

단일 워커는 LNS, LP 병렬 실행 등 CP-SAT의 핵심 강점을 버리는 것과 같다. 재현성이 필요하면 random_seed 고정 + 충분한 paired 테스트로 변동을 통계적으로 흡수하는 것이 낫다.

안티패턴 4: AddHint를 warm-start로 오해

model.add_hint(var, value)는 솔버에 초기 탐색 방향을 제안할 뿐이다. 모든 변수를 커버하지 않으면 힌트가 소리 없이 무시된다. Presolve 후 변수가 제거되면 해당 변수에 대한 힌트도 사라진다. MIP solver의 warm-start와 달리, 힌트가 feasible 해를 직접 주입하지 않는다.

안티패턴 5: FEASIBLE을 실패로 해석

시간 제한으로 인해 FEASIBLE이 반환되더라도 매우 좋은 해일 수 있다. solver.best_objective_bound로 gap을 계산해 해의 품질을 판단해야 한다. OGC에서 TL=120s 내 FEASIBLE 해도 경쟁자와 비교 가능한 수준일 수 있다.

안티패턴 6: 너무 크거나 중복된 도메인

변수 도메인을 [0, 10^9]로 막연하게 잡으면 CP-SAT presolve와 LP bound 생성에 악영향을 준다. 사전에 인스턴스 데이터로 도메인 상한을 빡빡하게 조여주면 탐색 속도가 크게 향상된다. OGC에서 HORIZON은 스케줄 최대 길이(max(D_i) + 여유)로 정확히 계산해 설정한다.
