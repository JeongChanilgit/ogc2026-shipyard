2. 시간은 어디로 가는가 — prob_20 단계별 벽시계 (300s)

가장 큰 인스턴스. 한 단계(seeds_decode)가 예산의 60%를 먹는다.

핵심 낭비: seeds_decode 178초는 여러 개의 독립적인 "씨앗 배정(seed)"을 1개 코어에서 순차로 crane-safe 디코드하는 시간이다 (300블록 한 베이 디코드 ≈ 30~40초 × 약 5개 씨앗). 이 단계가 만드는 incumbent는 Z1=424 — 형편없다. 그 뒤 postprocess(cum_level 등)가 그걸 Z1≈10으로 고친다. 즉 178초 단일코어 디코드가 만든 베이스를 postprocess가 거의 갈아엎는다.

3. 단계별 Z1 추적 — Z1이 어느 단계에서 떨어지나

파이프라인을 따라 Z1(=Σ tardiness)이 어떻게 줄어드는지. (gated: 각 단계는 목적함수를 악화시키지 못함)

읽는 법: search(seeds_decode 포함)가 높은 Z1을 오랜 시간 들여 만들고, cum_level + bbox_pack + cross-bay가 실제로 Z1을 끌어내린다. 즉 무거운 search 단계의 한계효용이 낮다 — 시간을 거기서 빼서 (a) 병렬화로 회수하거나 (b) Z1을 실제로 내리는 레버에 재배치하면 이득.

4. 낭비를 어떻게 손대나 + 시간 가속

① seed 디코드 4코어 병렬화 최대·최안전

지금 seeds_decode는 독립적인 씨앗들을 1코어 순차 디코드(178s). 평가서버는 4코어. 이미 인프라 존재(parallel_decode.py, run_parallel_multistart). 씨앗 디코드를 4코어로 fan-out → 178s → ~45s.

→ ~130초 회수. gate가 정답을 소유하므로 순수 speedup(회귀 위험 0). 회수한 예산은 곧 Goal 1의 무거운 레버(slab) 재원.

② 저가치 씨앗 가지치기 / 디코드 시간 캡

5개 씨앗을 다 풀디코드하지 말고, incumbent를 못 이길 씨앗은 짧은 캡으로 끊거나 건너뛴다. cum_level이 어차피 incumbent를 재디코드하므로, 초기 씨앗 품질의 한계효용이 낮다.

위험: 일부 regime에서 특정 씨앗이 feasibility 보강용 → 캡은 보수적으로.

③ seeds_decode를 병렬 multistart에 흡수

이미 run_parallel_multistart가 4코어에서 씨앗들을 디코드+로컬서치한다(현재 17s). 순차 seeds_decode(178s)는 그와 일부 중복 — 인큐번트 선택을 병렬쪽으로 합치면 178s 단계를 통째로 제거 가능.

④ cum_level 예산 캡 (70%→적정)

cum_level은 70초 쓰지만 수렴 후 한계효용 체감. STAGE_OBJ로 "개선 멈춘 시각"을 재서 조기종료 → 추가 예산 회수. (수렴추적은 트레이스에 이미 있음)

종합: ①+③만으로 prob_20 기준 ~130초를 안전하게 회수. 이는 (a) 속도 자체 개선이고, 동시에 (b) Goal 1의 막힌 케이스를 풀 예산이 된다.

5. 왜 이게 Goal 1과 직결되나 — slab 패커의 교훈

발견: tardy 블록은 전부 bbox(직사각) 낭비 97~136%인 베이에 몰린다. 폴리곤에 밀착하는 slab cover 패킹으로 공간을 회수하면 동시 적재가 늘어 조기 진입 → Z1↓.

오프라인 증명(노이즈 없음): prob_15 bay2 2→0 (최적 증명), prob_13 bay3 9→1.

그러나 엔드투엔드 실패: slab CP-SAT가 큰 베이에서 느려서, 검증된 cross-bay·cum_level이 쓸 예산을 잡아먹음. prob_13: slab-ON 258 vs slab-OFF 10 (150s). gate가 스테이지별 회귀는 막지만 다른 레버에서 뺏긴 예산은 못 막는다. → OGC_SLAB_PACK 기본 OFF로 안전 복원(코드는 opt-in 보존), 51개 테스트 통과.

결론: slab의 발목을 잡은 건 capability가 아니라 예산 부족이다. §4의 가속으로 예산을 비우면 slab(및 다른 Z1 레버)이 다시 viable 해진다. 그래서 "낭비 정리/가속"이 Goal 1의 열쇠다.
