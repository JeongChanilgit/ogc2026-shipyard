컴포넌트 타이밍 + 시퀀스별 목적함수 감소

측정: prob_38 (saturated, 107블록 베이) · greedy + postproc 120s · 제출 config(moveall+AABB) · 2026-06-24 · v7

두 줄 결론
① 시간의 ~72%가 CP-SAT(solve 42% + 모델빌드 30%) — disjunction 2만개가 좌우. 줄이려면 모델 크기↓(품질 trade-off). shapely 17%는 AABB로 −45%(안전).
② obj 감소는 postproc txyo가 거의 다(−6.8M), 그중 첫 300s에 −6.1M(앞쪽 집중). moveall +0.35M, cross-bay가 z3 주력.

각 컴포넌트 줄이는 법

  • CP-SAT solve (42%) — ortools C++, numpy 불가. 레버 = disjunction 수↓(=active 블록·후보 수↓ → 모델 작아짐). ⚠ solve 시간만 자르는 건 역효과(cap_scale=0.3 테스트 → worse plateau −2.36M). 시간이 아니라 모델 크기를 줄여야.
  • CP-SAT 모델빌드 (30%) — 2만 disjunction을 Python으로 생성(NewBoolVar·OnlyEnforceIf·AddBoolOr). 역시 disjunction 수↓가 직격. (saturated 베이서 191K combos→21K stored이 원흉.)
  • shapely 기하 (17%+5%) — precompute의 충돌/크레인 폴리곤 교차. AABB 사전필터로 precompute −45% 검증(동일출력·안전). 더 줄이려면 비트마스크 래스터 필터(saturated 베이용, 미검증).
  • greedy/numpy (5%) — 이미 numpy+FFT. 여지 작음.
★ 핵심 레버 = active 집합/후보 수 축소
saturated 베이의 all-active 패스(108블록·후보5개 → 191K combos · 21K disjunction · solve 11.8s)가 solve+build 둘 다의 원흉. active를 tardy 근처로만 좁히거나 후보를 줄이면 solve+build 동시 감소. 단 검색 범위↓라 품질 trade-off → 15분 A/B 필요. (cap 단축은 이미 실패했으니, 모델 크기로 접근.)

3. AABB 검증 (사용자 의심 확인)

AABB는 obj를 안 떨굽니다 — 확인됨.
  • 동일출력 증명: precompute에서 stored(저장된 disjunction 수) AABB off/on 완전 동일(20880). 모델이 같으니 해도 같음.
  • 10분 A/B (중단, partial): prob_38 t=300 AABBoff 55.30M ≈ AABBon 55.35M (차이 0.05M = CP-SAT 4워커 노이즈). 악화 없음.
  • 원리: AABB는 떨어진 페어의 shapely만 건너뜀 → 그건 원래 all-False(저장 안 됨) → 결과 불변, precompute만 −45%.
속도 이득은 작음(precompute가 전체의 17%뿐) — but obj 무해하니 켜두면 됨.

4. 결론 — 어디를 줄일까

  1. 최대 레버 = CP-SAT 모델 크기(disjunction 2만개 = 시간 73%). active 집합/후보 축소 → solve+build 동시↓. 품질 trade-off라 15분 A/B로 검증해야(시간만 자르는 cap은 실패 확인).
  2. 안전 속도 = AABB(precompute −45%, obj 불변) — 이미 켬. 추가로 비트마스크 래스터 필터(saturated 베이) 가능(미검증).
  3. obj는 postproc txyo가 다 함(첫 300s 집중). 그리디·타이밍은 −1.5M, 나머지 −6.8M이 txyo. moveall이 +0.35M 보탬.
  4. greedy·numpy(5%)는 이미 최적, 손댈 가치 작음.
