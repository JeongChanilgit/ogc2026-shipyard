제출본 v3 (postproc crane_repack) 구조 — 왜 빠른가

2026-06-23 · submission_build/postproc.py 해부 + v5 STEP2가 차용한 기법
한 줄: v3는 tardy(지각) 있는 베이만 · 그 시간창 블록만 풀어서 · 작은 후보(K=5)로 · 적응형 시간 캡을 걸고 CP-SAT 재패킹한다. 그래서 96블록 베이도 베이당 수십 초로 끝난다. 내 v5 STEP2가 느렸던 건 정반대로 모든 베이 · 전체 블록 free-all · iters=3로 돌려서였다.

1. 전체 구조 — postprocess() → _run_loop() 라운드 루프

def postprocess(prob_info, solution, deadline):
    bays_placed = adapter.deserialize(prob_info, solution)   # 해 → per-bay 배치
    best, best_obj = _run_loop(prob_info, bays_placed, base_obj, deadline)
    return serialize(best) if best_obj < base_obj else solution  # never-worse
_run_loop: while time < deadline 라운드 반복. 매 라운드:
▼
C3 (cheap, 먼저) — tardy 블록을 모든 fit 베이로 crane_repack 이동 ~2s
전-베이 z1 cross-bay 수리 (내가 추가). free_ids=1블록이라 빠름.
▼
C1 (SPATIAL) — tardy 베이만 x→y→o 좌표하강 crane_repack 핵심
위치+시각 재최적화로 z1↓. 아래 "빠른 이유" 전부 여기 적용.
▼
C2 (CROSS-BAY) — tardy/wrong 블록 move/swap (선호베이로) ~중
z3·z1 동시 — 선호베이로 옮겨 페널티↓.
▼
never-worse 게이트 — 각 trial은 공식 obj가 엄격히 개선될 때만 채택 안전
xyo는 라운드당 1번. 여러 라운드 = 반복 정제. (내 v5는 STEP2 안에서 iters=3을 또 돌려 중복이었음)

2. 왜 빠른가 — 4가지

① tardy 베이만 재패킹
bays_t = [(j, _bz1(pl)) for j,pl ...]
bays_t = [(j,z) for j,z in bays_t if z>0]
z1=0 베이는 통째 스킵. prob_38 4베이 중 지각인 2~3개만 손댐. (postproc.py:137)
② window_tardy_only=True
지각 시간창의 블록만 자유변수, 나머지는 상수로 동결 → CP-SAT 모델이 작음 → 솔브 빠름.
내 v5는 free-all(96블록 전체 변수) → 거대 모델 → 30초 캡 꽉 채움.
③ _pass_cap 적응형 시간
size_cap   = min(40, max(12, .3·n))
budget_cap = remaining/(2·n_active)
ts = max(8, min(size_cap, budget_cap))
베이 크기 와 남은예산 양쪽으로 자동 제한. (postproc.py:51)
④ K=5 작은 후보 + 축별 분리
축당 후보 5개(x만/y만/o만) → combo 작음. (joint 3축은 17만 combo로 폭발)

4. 시간이 어디서 걸렸나 (prob_38, 차용 전)

단계이 단계 소요비고
STEP1 배정 + greedy 초기배치4s빠름
STEP2 (xyo CP-SAT)~160초/패스모든 베이 free-all → 병목
STEP3 (tardy 재배정+greedy)~2~3초거의 공짜

STEP3가 아니라 STEP2가 시간의 ~98%였다. v3 기법(tardy-only + window-only)으로 STEP2를 줄이는 게 정답.

결론 — 제출본 v3가 빠른 비결 = "고칠 곳(tardy 베이·그 시간창)만, 작게, 예산만큼만" 푼다. v5 STEP2가 이 원칙을 어겨(전부·크게·30초씩) 느렸고, 이제 차용해 동일하게 빠르게 만들었다. 측정 결과는 v5-devlog.html에 누적.
